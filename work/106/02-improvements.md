## 3 ways FOR
1. **Close the tool-set path in `_field` itself: every `- ` item line of a `tools:`/`disallowedTools:` block list must have the same lead indent as the first item. Otherwise return a named error. Keep R1's S-2 stack for the other keys.**
   - Basis: YAML 1.2.2 §6.1, "All sibling nodes must use the exact same indentation level." [https://yaml.org/spec/1.2.2/] (R1 F20). The orchestrator measured the s2 shape: ParserError in the pure loader. Spanish (tecnoyfoto) states the same rule for list dashes: "Ambos guiones están alineados porque ambos valores pertenecen al mismo nivel." [https://tecnoyfoto.com/estructura-y-sintaxis-de-yaml] (WebFetch).
   - Why put it in `_field` as well as in the stack: `_field` is the function that turns lines into tool names (tests/test_agent_tools.py L112-L125). Today it reads every `- X` line at any indent (L121, L125), so a check there protects the tool set even if the stack in `_frontmatter_error` has a bug. It also closes R1 F11 / OQ5 (`tools:` / `  - Read` / `      - Bash` → {Read, Bash}) at no extra cost. R2 trace (not run): that line has indent 6, not 2, so the rule fails it. YAML is predicted to fold it into the scalar `Read - Bash` (R1 F11, by analogy with the measured e1). The stack cannot catch F11, because the line is a continuation (6 > 4) and has no colon.
   - Proposed fixture f1 `_fm("tools:", "  - Read", "      - Bash")` → the `_field` indent error. Only the new `_field` check kills it, so it gives mutation M78 (check removed) a unique kill. s2 is killed by M73 and M78 together, so it cannot be the unique pin for either.
   - Real tree cost: 0. R1 F12: every real `tools:` value is on one line (L4), with no block list. RI-001 count: 0 of 7 files, 0 of 21 frontmatter lines.
2. **For S-1, take rule B (R1's recommendation), applied to the plain text left after quote handling. Align it with the quoted-value policy that has shipped since 080.**
   - PyYAML's own scanner says tabs are refused on purpose. Source comment: "We just forbid them completely. Do not use tabs in YAML!" `scan_plain_spaces` accepts only `' '` between words (`while self.peek(length) in ' ':`), and `scan_to_next_token` skips only spaces (`while self.peek() == ' ':`) [https://raw.githubusercontent.com/yaml/pyyaml/main/lib/yaml/scanner.py] (WebFetch reading of main, not 6.0.1). So `a\tb` and a trailing `a\t` are predicted to raise in the pure loader just as `a\t# c` does. That prediction matches R1 F16 and is still UNVERIFIED until I2 probes it.
   - A real project hit the trailing-tab case. HEPData issue "requirements: pin PyYAML and add a test for a trailing tab" quotes "yaml.scanner.ScannerError: while scanning for the next token found character '\t' that cannot start any token", and the fix it gives is "The problem is avoided by using LibYAML, for example, `yaml.CSafeLoader` instead of `yaml.SafeLoader`." [https://github.com/HEPData/hepdata/issues/314] (WebFetch). So the shape occurs in real files, and the two loaders split on it. That split is the "unreadable" case of RI-002.
   - Consistency with code that already shipped: AFTER_CLOSE_RE `( +#.*)? *` (tests/test_agent_tools.py L86) already refuses a tab after a closing quote (`"x"\t`, item 080). That is the exact case where the YAML co-author says libyaml is right and PyYAML is wrong (AGAINST 1). Rule B therefore applies the existing quoted-value policy to plain values. Rule A would leave `a\tb` passing while `"a"\tb` fails, which is an inconsistency R3 would have to document.
   - Portuguese gives the reason a disagreement is likely in general: "sistemas diferentes interpretam tabs de formas distintas" [https://www.datacamp.com/pt/blog/what-is-yaml] (WebFetch). Cost on the real tree: 0 tabs (R1 F12).
   - Simplification for R3: one helper, "a tab in the text outside quotes and before the first comment start (a `#` preceded by a space or tab)". Call it from the three places R1 lists (plain value in `_node`, the continuation branch, the block header), so M69 removes one function and fails w1-w5 and w6 at once. The alternative is three copies plus a BLOCK_RE edit, which makes M72 a separate surface.
3. **For S-3, take R1's `in_flow` flag, but clear it with `_field`'s own end-of-field rule, not with "the next column-0 line that is not FLOW_KEYS".**
   - `_field` stops a field only at a line that does not start with a space or tab and is not an item (tests/test_agent_tools.py L117-L118, `line[0] not in " \t" and not _is_item(s)`). A column-0 `- Read` under `tools:` is still part of the field (it is legal YAML at column 0, measured v18/v19, R1 F21). Under R1's rule as written (01 L85), that `- Read` line clears `in_flow`.
   - R2 trace (not run), fixture c5 `_fm("tools:", "- Read", "      Bash: x")`. `- Read` is at column 0 and is not FLOW_KEYS, so R1's flag clears. `_node` gives col 2, closed. `      Bash: x` has ind 6 > 2, so it is a continuation, and `_plain_colon` gives VALUE(4). If the flag uses `_field`'s rule instead, the line is skipped and `_field` returns `unparsed tools: line 'Bash: x' (item 075)` (L121-L122), which is the message the request asks for.
   - Proposal: one helper, for example `_ends_field(line)` = `line[:1] not in ("", " ", "\t") and not _is_item(line.strip())`, plus the blank/comment skip. `_field` and the flag both call it, so a mutation to it (M77') breaks c4 and c5 together, and the two rules cannot drift apart. This is a reasoning chain from the repo text, with no outside source.

[https://bitbucket.org/snakeyaml/snakeyaml/issues/487/does-not-flag-trailing-tab-character] (WebFetch).
