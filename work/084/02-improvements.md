## 3 ways AGAINST
1. **Any history-based exemption is a loosening, and RI-010 is about exactly that.** The anchor makes "not checked" a computed result, not a named one. A future branch cut from an old main can then be exempted without anyone writing it down, which is what 049 avoided with a closed list ("never add", L238). Reasoning: once main has the rule, a new item built on a stale branch would also count as "not seen". The 051 `MAIN AHEAD` line and the 049 rule are meant to stop that, but 083 shows they can be skipped. Mitigation, required: the RULE NOT SEEN line plus the exact-set self-test (FOR 3d). Any new exemption on HEAD then fails a test, and someone has to look at it and update the pinned set in the open. With that pin the general mechanism is no looser than a closed list.
2. **A closed named exception is cheaper and has a precedent.** The 049-style option would be `RULE_EXCEPT = {"083": "built on main (PR #34) before 071/076 reached main (item 084)"}`, about 5 lines, no git, the same answer with or without git. It meets "Done looks like" for 083 (request L17). It does not meet the request's fixture (an item merged on main while a rules branch is open is not flagged, with no hand edit), and it does not stop the next parallel main item from turning PR heads red. An item 049-style rewrite of 083's artifacts (a new I2 line, a `Sent back to: none` line) would hold 083 to rules it never had, and it would need A1 to re-decide 083's tests field (R1 finding 2). Verdict: the general anchor, because the request asks for a guardrail and not a one-off. I1 may fall back to the closed list only if FOR 1's tree test fails on real history (UNVERIFIED checks in FOR 1c). If so, write it down as a decision.
3. **The result depends on the environment, which is RI-014's failure mode in reverse.** Without git (a tarball) or in a shallow clone, FOR 3a gives the numeric cutoff, so `INCOMPLETE: 083` comes back there while a full clone says none. Also, in a shallow clone `git log --diff-filter=A` can name the boundary commit as the one that "added" every file, and that commit's tree has the rule. So shallow has to be detected first (`--is-shallow-repository`, as `_inbox_gate` L995-999 does), not inferred. Reasoning: in a shallow clone the boundary commit has no parents in the local history, so its files look added (R1 finding 18; exact git behaviour UNVERIFIED here). This direction is loud, not silent (a false INCOMPLETE, never a false pass), and the printed note says why. It is still a difference in results, which A1 must not record as a regression. The daily audit already unshallows first (079's process line).
