## Decision: the exempt set and per-constant precision (orchestrator's question)
The 8 measured anchors show that "not seen" (the constant is absent at the add commit) covers **{073 (VERDICT_FROM), 083 (both)}**. The map does **not** pin {073, 083}, for three reasons:
1. 073 passes 071's rule as it stands (it is not INCOMPLETE on b2f11b9; only 083 is named). Exempting an item that passes nothing-to-exempt only adds noise. A pinned set that grows with history, rather than with suppressed failures, would teach readers to update it without looking.
2. An unseen item is judged by **the rule in force at its add commit** (the below-cutoff branch: I2_BEFORE for the I2 field, no verdict-line check below VERDICT_FROM, gap (y)). It is not "not checked at all". So 083's I2 line is still checked, against I2_BEFORE, which it passes (344 <= 344).
3. RULE NOT SEEN lists an (item, rule) pair only when the new rule fails and the gate changed the result. On HEAD that is exactly {083: 076, 071}. If 073's 06 is later edited so that it fails 071's rule, 073 shows up in the line, the exact-set test fails, and someone has to look. That is the RI-010 safeguard.

Per-constant precision is required. Each rule checks its own constant (`^VERDICT_FROM = ` in 06's add-commit tree, `^TESTS_FORMAT_FROM = ` in 05's add-commit tree), never the combined regex. The orchestrator's combined count of 1 for 071 can't tell the two constants apart. The rename hole (mutation 2) is caught by the positive control on 076 (combined count 2, so both constants are present: unambiguous).
