## 3 ways FOR
1. (b) is safe by construction and matches pytest's documented output. pytest prints `N deselected` in the final summary of every `-k`/`-m` run, including when N is 1. The official docs show `3 passed, 1 deselected in 0.12s` and `2 passed, 2 deselected in 0.12s` [https://docs.pytest.org/en/8.3.x/example/markers.html]. The deselected part comes right after `skipped` in KNOWN_TYPES [01 finding 11]. Each such line is a real run that took real time, so counting it can only raise Σ. It cannot cause a false flag [01 finding 10]. Measured: 72 in-section runs that LOG BATCH reads past today would become visible, at zero risk of a false flag (all `same=True`).
2. (b) closes a future blind spot that the data has not hit yet. If a 05 or 06 contains only targeted runs (for example an I3 that re-runs only the changed test file with `-k`), `_run_seconds` returns no value for that file. Then `known` loses that file's term, or, if both files have no value and no I2 field matches, the item becomes `not_computable` with "no pytest time in 05/06/I2 line" [scripts/check_pipeline.py L1446-1450, L1583-1585]. That file's run time then never reaches Σ. Today no item has this shape (`not_computable same=True`). The reasoning comes from the code path. How often this would happen in future is UNVERIFIED.
3. A (b) change is small and cheap. It is one inserted `{N} deselected` part in `_STATS_PARTS` order, and the script's self-test already exercises it with 6 fixture strings (01 L49-55). Since `--log` refuses `deselected` in the I2 field [01 finding 8], the I2 path through SUMMARY_LINE (L1577-1581) sees no new input. Results: 0 flag changes, 0 max changes, and the `*_FROM`/`_rule_seen` gate is not needed (01 open question 3).

## 3 ways AGAINST
1. (a) has no measured benefit. All 4 lines under a bare wrapper are Q (mutants in scratch copies, 084/05 L234-250), at 092-098 and at >=099 the count is 0, and the one >=099 wrapper (104/06) has its suite under a read `## Tests re-run (round 2)` opener [01 finding 6]. Any summary-line rule under a wrapper would flag those 4 correctly quoted lines on old data and catch nothing new. That fails the decision rule in 01 open question 1 and request L11, the same way 103's narrow rule failed. A heading-wording rule that exempts `mutation` repeats 103's AGAINST 3: it costs more than it covers [work/103/02-improvements.md L64].
2. (b) changes no outcome. 0 of 34 affected files change their max, and LOG BATCH's output is identical. The reason is built in: Σ uses the largest time per file, not a sum [scripts/check_pipeline.py L1583], and deselected runs are short partial runs (in this data 0.07-23.78 s, against full suites of 80-120 s [logs/audit/2026-11-25-103.md L45; work/103/02-improvements.md L24-44]). So the rule would add a fixture, a mutation and a regex change to a shared constant, with a measured effect of zero. The design comment at L465 ("a full-suite run has none") states the current choice on purpose [01 finding 8].
3. (b) moves a shared regex and can subtly lower Σ through the copy filter. `kept06` drops every 06 time that equals any t05 time to 2 decimals (L1582). With deselected 05 times added to t05, a 06 full-suite time that happens to equal a 05 deselected time to the hundredth would be dropped as a "copy". t06's max would then fall, and Σ could fall, which means a missed flag. That is the very failure (b) is meant to prevent. This is a reasoning chain, and the measurement shows it did not happen in 059 items. Separately, SUMMARY_LINE is shared with the I2 field path (L1579) and with item 103's pinned docstring test [logs/audit/2026-11-25-103.md L34-36], so a change needs a re-check of every test that pins it.
