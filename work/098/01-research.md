## Findings (one claim per line, each with [source URL] or UNVERIFIED)
### Sub-ask 1: trailers through commit-tree
- 1.1 commit-tree's synopsis is `git commit-tree [(-p <parent>)…] [-S[<keyid>]] [(-m <message>)…] [(-F <file>)…] <tree>`. It has no `--trailer` option: none appears in SYNOPSIS or OPTIONS. [https://git-scm.com/docs/git-commit-tree]
- 1.2 commit-tree: "`-m <message>`: A paragraph in the commit log message. This can be given more than once and each <message> becomes its own paragraph." `-m` and `-F` "can be given any number of times, in any order", and the message is built in that order. [https://git-scm.com/docs/git-commit-tree]
- 1.3 commit-tree reads the message from stdin "unless `-m` or `-F` options are given". `-F -` reads stdin, and each `-F` file becomes its own paragraph. [https://git-scm.com/docs/git-commit-tree]
- 1.4 interpret-trailers: "A *trailer* in its simplest form is a key-value pair with a colon as a separator. The *key* consists of ASCII alphanumeric characters and hyphens (`-`). ... The trailer block needs to be preceded by a blank line". [https://git-scm.com/docs/git-interpret-trailers]
- 1.5 interpret-trailers: "The trailer block is by definition at the end of the commit message." A block counts if it "(i) is all trailers, or (ii) contains at least one Git-generated or user-configured trailer and consists of at least 25% trailers." [https://git-scm.com/docs/git-interpret-trailers]
- 1.6 Consequence of 1.2 + 1.5 (inference from the two docs, to be pinned by a test): one `-m` per trailer would put each trailer in its own paragraph, and only the last paragraph is the trailer block. So all trailers must go in one final `-m` (lines joined by `\n`), or the message must go through `git interpret-trailers`. Whether git recognises earlier one-line paragraphs too is UNVERIFIED; the docs say only that the block is at the end. [https://git-scm.com/docs/git-commit-tree] [https://git-scm.com/docs/git-interpret-trailers]
- 1.7 interpret-trailers `--trailer`: "Specify a (<key>, <value>) pair that should be applied as a trailer to the inputs ... Can be given multiple times." It is "appended after the existing trailers", and a blank line is inserted before a new block (doc example: `echo "subject" | git interpret-trailers --trailer fix=42`). It reads stdin when no file is given. [https://git-scm.com/docs/git-interpret-trailers]
- 1.8 interpret-trailers: by default only `:` is a separator, "except that `=` is always accepted on the command line". A `trailer.*` config can change where trailers go and whether duplicates are dropped (git-commit `--trailer` text: "The `trailer.*` configuration variables ... can be used to define if a duplicated trailer is omitted"). [https://git-scm.com/docs/git-interpret-trailers] [https://git-scm.com/docs/git-commit]
- 1.9 `git commit --trailer` exists ("will add the `Signed-off-by` trailer and the `Helped-by` trailer"), but commit_step does not use `git commit`: it uses a temporary index plus `commit-tree` and `update-ref` (scripts/commit_step.py L172-189), so the git-commit option does not apply. [https://git-scm.com/docs/git-commit]
- 1.10 Why the amend has been safe so far: "If this option [--only] is specified together with `--amend`, then no paths need to be specified, which can be used to amend the last commit without committing changes that have already been staged." 091 A1 checked each amend's tree against the helper commit's tree (4 reflog pairs, trees equal). [https://git-scm.com/docs/git-commit]; logs/audit/2026-11-22-091.md L10-15
- 1.11 git-commit DISCUSSION: "The text up to the first blank line in a commit message is treated as the commit title". So trailers added after a blank line leave the subject unchanged, and the item-082 subject rule in commit_step (`subject == "Item <ID>: " + own line`, L170) still compares the same text. [https://git-scm.com/docs/git-commit]
- 1.12 A test can read trailers back with `git log -1 --format=%(trailers:key=<k>,valueonly)` ("display the trailers of the body as interpreted by git-interpret-trailers"; `key=` matching is case-insensitive), check the subject with `%s` and the raw message with `%B`. [https://git-scm.com/docs/pretty-formats]
- 1.13 Repo today: `commit()` calls `_git(run, ["commit-tree", tree, "-p", old, "-m", subject])` (L188); `main()` takes `argv[0]` = ID, `argv[1]` = subject, `argv[2:]` = paths (L209-213). There is no option parsing, so a `--trailer` argument would be taken as a path and refused as `not found` by L161. Repo fact (scripts/commit_step.py).

### Sub-ask 4: HEAD label and docstring
- 4.1 rev-parse `--verify -q`: "Do not output an error message if the first argument is not a valid object name; instead exit with non-zero status silently." The docs give no exit number, so "exits 1" for an unborn HEAD is measured, not documented. [https://git-scm.com/docs/git-rev-parse]
- 4.2 git API: "`die` is for fatal application errors. It prints a message to the user and exits with status 128." `usage` exits 129. This fits the 128 that 088 A1 measured for `git ls-tree HEAD` on a corrupt ref and on a dangling symbolic HEAD. [https://git-scm.com/docs/api-error-handling]; logs/audit/2026-11-21-088.md L70-78
- 4.3 symbolic-ref: "exit with status 0 if the contents of the symbolic ref were printed correctly, with status 1 if the requested name is not a symbolic ref, or 128 if another error occurs." The page says nothing about a symbolic ref whose target does not exist (an unborn branch). [https://git-scm.com/docs/git-symbolic-ref]
- 4.4 Inference, UNVERIFIED: an unborn branch and a "dangling symbolic HEAD" (HEAD -> refs/heads/<missing> in a repo with commits) look the same at the HEAD ref, so separating them needs extra reads (other refs, objects). A corrupt ref file is a third case. Each extra git call would change the call census pinned by `test_git_call_census` (088). The low-cost option 088 A1 suggested is a neutral label: "HEAD names no commit (unborn or unresolvable)". logs/audit/2026-11-21-088.md L98-105
- 4.5 Docstring state on this branch: `_anchor_env` (L795-805) already says "non-zero; 128 measured on a corrupt ref and a dangling symbolic HEAD ... item 091" and "Both print `not checked (unborn HEAD)`; the label is not accurate for the second (follow-up, not changed here)". So the "exits 1" wording was fixed in 091, and only the label (L816, module text L327-328) remains. The `(exit 1)` in the UNCOMMITTED STEP text (L288-289) is the script's exit code, not ls-tree's. Repo fact.
- 4.6 Tests that pin the current label exactly and would change: `test_rule_anchor_unborn_head_is_strict` (tests/test_pipeline_check.py L2858-2879: `"RULE NOT SEEN: not checked (unborn HEAD)"`, `_anchor_env() == ("unborn HEAD", False)`), and the parametrize row at L2399.
