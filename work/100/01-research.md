## Question
`_build_waived` (item 062) decides whether a RESEARCH ONLY item that changes code has the person's `Waived: 04 05 06 (person, <date>: <why>)`. A1 (logs/audit/2026-11-24-093.md F1) found that it returns True for `Waived: 04 05 06 (person: x "(person, 2026-11-19: ok)")`. That line has no dated person form at its first parenthesis; the dated form appears only inside quoted text. Questions:
(a) Why does the code accept it, and what is the smallest anchored fix?
(b) Does the fix change any real item's output (work/062, work/024, and any other real `Waived:` line)?
(c) Which test and mutation pin it (RI-012)?
(d) F2: how should 093's N-g fixture change so that it alone shows an unreadable request.md is never excused?

This is a repo-internal bug in scripts/check_pipeline.py. Every finding below cites a repo file and line, read on branch daily-fixes/2026-11-24-b on 2026-11-24. Only the Python regex and UTF-8 facts have web sources. I had no shell in this run, so the behaviour claims are from reading the code. A1 ran the F1 probe (finding 4). The rest were not run by me and are marked "by reading".

## Findings (one claim per line, each with [source URL] or UNVERIFIED)
1. `WAIVE_BUILD_BY_PERSON = re.compile(r"\(\s*person\s*,\s*\d{4}-\d{2}-\d{2}\s*:")` has no anchor. `_build_waived` returns `WAIVE_BUILD <= set(steps) and who == "person" and bool(WAIVE_BUILD_BY_PERSON.search(waived_line))`, and `waived_line` is the whole first `Waived:` line. [repo: scripts/check_pipeline.py L536-537, L624-628]
2. `who` comes from `re.match(r"\s*\(\s*([^,:)]+)", waived.group(2))`: the text after the first `(`, up to the first `,`, `:` or `)`, stripped and lower-cased. For `(person: x "...")` the class stops at `:`, so `who` is "person". [repo: scripts/check_pipeline.py L612-621]
3. So for the F1 line all three conditions hold. The steps are {04, 05, 06}, `who` is "person", and `.search` finds `(person, 2026-11-19:` inside the quote. The who check guards only against a different first who (062's `(I2, ... copied "(person, ...)")` case). It cannot catch a person-first line that has no date. [repo: scripts/check_pipeline.py L617, L628; work/062/06-verification.md L47-54]
4. A1 reproduced it on 1b10d90: `_build_waived('Scope: RESEARCH ONLY\nWaived: 04 05 06 (person: x "(person, 2026-11-19: ok)")\n')` returns True. 093's R2 (FOR1), R3 and I3 found the same hole, and I3 probed it. [repo: logs/audit/2026-11-24-093.md L58-62; work/093/06-verification.md L109; work/093/03-handoff.md L42]
5. Python's `re.search` will "Scan through *string* looking for the first location where the regular expression *pattern* produces a match". `prefixmatch()`/`match()` "checks for a match only at the beginning of the string". [https://docs.python.org/3/library/re.html]
6. `re.match` is "Soft deprecated since version 3.15" in favour of `prefixmatch()`, but the docs say "code supporting older versions of Python should continue to use `match()`". The project declares Python >= 3.10 (RI-008), so the fix should use `.match`, as 093's PERSON_DATED comment already says. [https://docs.python.org/3/library/re.html; repo: logs/recurring-issues.md RI-008; scripts/check_pipeline.py L538-541]
7. 093 already built the anchored form. `WAIVED_LINE = re.compile(r"^Waived:\s*([0-9 ,]+)(.*)$", re.M)` (group 1 = step numbers, group 2 = the rest) and `PERSON_DATED = re.compile(r"\s*" + WAIVE_BUILD_BY_PERSON.pattern)`, "used only with .match on WAIVED_LINE group 2". `_person_waived_before_i2` uses `WAIVED_LINE.search(req_text)` and then `PERSON_DATED.match(m.group(2))`. [repo: scripts/check_pipeline.py L538-543, L631-645]
8. `parse_request` reads `Waived:` through the same `WAIVED_LINE.search` (first line only), so `_build_waived` and the 093 helper see the same line. [repo: scripts/check_pipeline.py L616]
9. Proposed fix (smallest, by reading): in `_build_waived`, replace `bool(WAIVE_BUILD_BY_PERSON.search(waived_line))` with `PERSON_DATED.match` on WAIVED_LINE group 2 of the same text, i.e. `m = WAIVED_LINE.search(text)` and `bool(m and PERSON_DATED.match(m.group(2)))`. Then update the docstring to say the dated form must start the text after the step numbers. [repo: scripts/check_pipeline.py L624-628, L640-642]
10. With the fix, the F1 line is refused. Group 2 is `(person: x "(person, 2026-11-19: ok)")`. PERSON_DATED needs `,` after `person`, finds `:`, and `.match` cannot move on to the quote. 093's `test_person_dated_anchor` already asserts `PERSON_DATED.match('(person: x "(person, 2026-11-19: ok)")') is None`. [repo: scripts/check_pipeline.py L543; tests/test_pipeline_check.py L4538-4545]
11. By reading, the 7 existing cases of `test_build_waiver_needs_person_date_and_all_three` keep their results under the fix. The two `(person, 2026-11-13: ok)` lines stay True: group 2 starts with that form. `04` alone stays False on the subset check. `(I2, ...: person said ok)`, `(person: ok)` and the copied `(I2, ... "(person, 2026-11-12: ok)")` stay False because group 2 does not start with the dated person form. The two-line case stays False: the first line `02 (A1, ...)` is read, and `.*` does not cross a newline. [repo: tests/test_pipeline_check.py L1215-1226; scripts/check_pipeline.py L542]
12. With the fix, the who check becomes implied. If `PERSON_DATED.match(group 2)` holds, group 2 starts with `\s*(\s*person\s*,`, so parse_request's `who` is "person". A mutation that drops `who == "person"` would then survive every test. Case is unchanged: `(Person, <date>: ...)` gives who "person" but is refused by the case-sensitive pattern, as today. [repo: scripts/check_pipeline.py L537, L543, L617, L621, L635-638]
13. `_build_waived` has one caller, `_research_code` L736. `_research_code` is used for HEAD commits and for open branches (062/05). [repo: scripts/check_pipeline.py L736; work/062/05-build-report.md L26]
14. Real `Waived:` lines in request.md: only work/023 (`02 (A1, 2026-10-31, ...)`, Scope RESEARCH ONLY) and work/024 (`01 02 03 04 (person, 2026-10-31: ...)`, Scope FULL). work/062/request.md is Scope FULL and has no `Waived:` line. [repo: grep `^Waived:` work/*/request.md and `^Scope:` work/{023,024,062}/request.md, 2026-11-24]
15. So the fix changes no real item's `_build_waived` result. 023 is False before and after: who is "a1" and 04-06 are not waived. 024 and 062 are FULL, and L736 calls `_build_waived` only for RESEARCH ONLY. 024's 093 result comes from `_person_waived_before_i2`, which the fix does not touch, and `test_person_waiver_helper_on_item_024` pins it. [repo: work/023/request.md L3-4; work/024/request.md L3-4; scripts/check_pipeline.py L736; tests/test_pipeline_check.py L4557-4563]
16. F2. In `batch_log_items`, the excuse is reached only when `_read(d / "request.md", missing_ok=True)` gives `why is None and text is not None`. [repo: scripts/check_pipeline.py L1552-1557]
17. `_read` decodes the bytes as strict UTF-8. On `UnicodeDecodeError` it returns `(None, "<path> unreadable")` and records `not UTF-8 at byte <n>` in `_UNREAD`. [repo: scripts/check_pipeline.py L593-609]
18. The byte 0xFF can never be valid UTF-8: "The octet values C0, C1, F5 to FF never appear." So any request.md holding it fails the strict decode. [https://www.rfc-editor.org/rfc/rfc3629]
19. 093's N-g fixture is `b"\xff"` alone. It has no Scope or Waived text, so even a reader that bypassed strict decoding (for example `errors="replace"`) would produce no waiver, and N-g would stay strict. N-g therefore cannot tell "unreadable is never excused" from "nothing to excuse". Only `test_read_census` catches such a bypass (A1). [repo: tests/test_pipeline_check.py L4586-4601; logs/audit/2026-11-24-093.md L53-55, L63-64]
20. A1 checked by probe that `_read` on `Scope: FULL\nWaived: 01 02 03 04 (person, 2026-11-20: t)\n\xff` returns `(None, "<path> unreadable")`, so the reason stays strict. [repo: logs/audit/2026-11-24-093.md L53-54]
21. `_waived_item` writes a bytes `req` as-is, with no header added, so `REQ_FULL_093.encode("utf-8") + b"\xff"` gives a file whose readable part is a valid FULL person waiver of 01-04. [repo: tests/test_pipeline_check.py L4500, L4503-4517]
