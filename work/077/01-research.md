### Point 4: one shared comment/fence-strip helper for `i3_verdict` and `_field_gap`
- F20. Both functions drop `<!--.*?-->` (re.S) and then toggle a fence on any line where `line.lstrip().startswith("```")`: `i3_verdict` at L286-294, `_field_gap` at L677-681 and L689-690. The `i3_verdict` docstring says "``` only (~~~ is not tracked, 0 in 06 files 2026-11-18)". [repo: scripts/check_pipeline.py]
- F21. The two callers use the fence state differently. `i3_verdict` skips fence marker lines and lines inside fences, and an unclosed fence just hides the rest. `_field_gap` finds its heading only outside fences, keeps fenced lines (and the marker lines) in the section, ends the section only on a `## ` outside a fence, and returns "unclosed ``` fence" as a failure. So the helper must give each line's state (outside / marker / inside) and whether a fence is still open at the end. It must not drop fenced lines itself. [repo: scripts/check_pipeline.py L282-305, L673-699; tests T4 L1590 (unclosed fence -> (None, None)) and test_t12_fences_and_headings tests/test_real_data_field.py L259]
- F22. CommonMark 0.31.2 §4.5: "A code fence is a sequence of at least three consecutive backtick characters (`) or tildes (~)". Backticks and tildes cannot be mixed. The opening fence may be indented by up to three spaces. [https://spec.commonmark.org/0.31.2/#fenced-code-blocks]
- F23. CommonMark §4.5 (paraphrased; my fetch returned a summary, not the exact sentence): the content ends at a closing fence of the same character (backticks or tildes) with at least as many characters as the opening fence. The closing fence may be indented up to three spaces whatever the opening fence's indentation, may be followed only by spaces or tabs, and cannot have an info string. [https://spec.commonmark.org/0.31.2/#fenced-code-blocks]
- F24. CommonMark §4.5: the info string of a backtick fence may not contain backtick characters. Tilde fences have no such limit. [https://spec.commonmark.org/0.31.2/#fenced-code-blocks]
- F25. CommonMark §4.5: with no closing fence, the block runs to the end of the containing block or document. This differs from `_field_gap`'s deliberate "unclosed fence fails" (item 070), which is stricter than the spec and should stay as a check on top of the helper. [https://spec.commonmark.org/0.31.2/#fenced-code-blocks; repo L694-696]
- F26. CommonMark: 4 or more spaces of indentation make an indented code block, not a fence (§4.4, "four or more spaces of indentation"). HTML block starts likewise allow "up to three spaces of indentation, but not four". [https://spec.commonmark.org/0.31.2/#html-blocks]
- F27. Behaviours the current toggle gets wrong under F22-F26: (a) `~~~` fences are not seen; (b) a ```` fence is closed by a later ``` line; (c) a ``` line indented 4+ spaces toggles; (d) a ```` ```lang ```` line closes an open fence. [derived: repo L290, L680, L689 vs F22-F26]
- F28. Impact on existing files, measured by grep on 2026-11-19: work/*/05 and 06 contain 548 lines starting (after whitespace) with ``` across 75 files, an even count in every file. 0 of them carry text after the backticks (```` ^\s*```\S ````), and 0 are indented 4+ spaces. There are 0 `~~~` or ```` lines in work/, templates/ or .claude/, and 0 fences inside blockquotes in work/. So the stricter rule should change no current verdict or field result. I could not run the suite or check_pipeline to confirm (no shell), and I2/I3 should diff check_pipeline output before and after. [repo grep; UNVERIFIED by a run]
- F29. Not handled by either the current code or a line-based helper: fences nested in list items or blockquotes (CommonMark containers, F25 "containing block"). Today there are 0 such fences (F28), so this would be a documented known gap, not built. [https://spec.commonmark.org/0.31.2/#fenced-code-blocks; repo grep]
- F30. Order hazard, also not new: comments are stripped before fences are tracked, so a `<!--` inside a fence with no `-->` on the same line would hide text up to the next `-->` anywhere. CommonMark treats fenced content as literal text, not HTML. In work/*/05 and 06 there is 1 line with both ``` and `<!--`: work/071/05 L7, inline code that holds `<!--.*?-->` on one line, so it is harmless. Moving comment stripping into the same line pass (outside fences only) would remove the hazard. CommonMark type-2 HTML block: start "line begins with the string `<!--`", end "line contains the string `-->`". [https://spec.commonmark.org/0.31.2/#html-blocks; repo grep; repo scripts/check_pipeline.py L286, L677]
- F31. Existing tests the helper must keep green: `test_i3_verdict_reader` (T4, parametrized, ending at L1604, including the unclosed fence L1590, the fenced FAIL L1592 and the comment L1593) and `test_t12_fences_and_headings` (tests/test_real_data_field.py L259). New ids are needed for `~~~`, a longer fence closed only by an equal-or-longer one, a 4-space "fence", and an info-string line that does not close a fence, for both callers. [repo]

### Point 5: `UNCOMMITTED STEP:` (074 resume near miss)
- F32. The near miss: an I3 round cut by a container restart left an uncommitted 06. The cut-off run left "no log line and no commit", and check_pipeline reads step files from the working tree, so "an uncommitted or untracked `work/<ID>/0N-*.md` ... counts like a committed one". The proposal is an `UNCOMMITTED STEP:` line for step files not in HEAD that have no matching log line. [repo: logs/audit/2026-11-18-074.md L27, L84]
- F33. The overlap I found: for items from CHECKLIST_FROM (41) on, `incomplete()` already reports `no log line for <agent>` for any step file 01-06 that exists in the working tree without its `| <agent> | <ID> |` line (L390-393). So a cut-off 06 with no I3 line already gives INCOMPLETE with exit 1, but the message names the wrong cause (a missing log line, not an uncommitted file from a cut-off run), and classify still counts the file (L350). The new line adds the cause and git state. Whether the old message should change is for R2/R3. [repo: scripts/check_pipeline.py L380-393, L350]
- F34. Defining "not committed": `git status` by default (`normal`) shows "untracked files and directories", and only `all` "also show[s] individual files in untracked directories". So `git status --porcelain -- work/` on a wholly new work/<ID>/ gives one `?? work/<ID>/` entry, not the files inside it. A parser would need `--untracked-files=all`. [https://git-scm.com/docs/git-status]
- F35. Porcelain v1 is "guaranteed not to change in a backwards-incompatible way between Git versions or based on user configuration". `??` = untracked and `A` = added to index (staged, not yet committed). Without `-z`, names with special characters are quoted "in the manner of a C string literal". With `-z` they are printed "as is". [https://git-scm.com/docs/git-status]
- F36. Simpler alternative: list HEAD's files with `git ls-tree -r --name-only HEAD -- work/` ("-r: Recurse into sub-trees"; "--name-only: List only filenames") and flag working-tree step files (STEP_FILE regex, L227) that are missing from it. This covers untracked and staged-new files in one rule, needs no `-uall`, and is not affected by porcelain status codes. Quoting of "unusual" characters (core.quotePath) does not matter, because STEP_FILE names are ASCII. `open_branches` already uses `ls-tree -r --name-only` (L531). [https://git-scm.com/docs/git-ls-tree; repo L227, L531]
- F37. The "no log line" condition keeps the normal flow quiet. I3 runs check_pipeline "after this file and your `--log` line are written" and before the orchestrator commits (i3-verifier L16), so its own uncommitted 06 has a log line and is not flagged. For no-Bash agents (R1, R2, R3, I1) the orchestrator runs `--log` right after the file exists (scratchpad brief L5; r1-researcher.md L19), so a run in that gap would flag it, which is correct. [repo: .claude/agents/i3-verifier.md L16; .claude/agents/r1-researcher.md L19]
- F38. Known gaps to write down, not build: (a) a cut-off run that wrote both the file and its log line but was not committed is not flagged; (b) a tracked file modified in a cut-off later round (e.g. a round-2 06) is in HEAD and already has round 1's log line, so neither condition sees it; (c) 07-audit-task.md is outside STEP_FILE (01-06) and has no agent log line. [derived from F32-F37]
- F39. Without git, other lines print "not checked (no git)" (L923-926), and this line should do the same. `ls-tree HEAD` works in a shallow clone because HEAD's tree is present, so it does not depend on 079's shallow-boundary handling. That last part is UNVERIFIED by a run. [repo L923-926; UNVERIFIED]
- F40. Open design choices for R2/R3: exit code (the RI-010 lines LOG TIME and INCOMPLETE exit 1, L935); whether classify should stop counting an uncommitted file without a log line; and whether the line covers items below CHECKLIST_FROM. [repo]
