### B. Git behaviour the fixtures rely on
7. `git rev-parse --verify`: "Verify that exactly one parameter is provided, and that it can be turned into a raw 20-byte SHA-1 ... otherwise, error out." [https://git-scm.com/docs/git-rev-parse]
8. `-q`/`--quiet`: "Do not output an error message if the first argument is not a valid object name; instead exit with non-zero status silently." The page gives no specific code. The code's `head[1] == 1` = unborn (L644) and the census reason "rev-parse --verify exit 1 = unborn HEAD" (tests L2394) depend on exit 1, which is UNVERIFIED from docs. Either way it fails strict: any other non-zero code gives `(None, "<step> anchor: git failed (item 084)")` (L646-648), which is strict plus an entry. The unborn fixture should pin which branch the installed git takes by asserting the exact INCOMPLETE text. [https://git-scm.com/docs/git-rev-parse]
9. `git log -1 -- <path>` shows "only commits that are enough to explain how the files that match the specified paths came to be". `-<number>` limits "the output to the first <number> commits that would be shown". The git-log page says nothing about the exit status when no commit matches. So "an untracked or staged-only path gives empty output, exit 0" (what L649-655 assumes) is UNVERIFIED from docs. The uncommitted fixture should pin it with a direct `subprocess.run`, as d2 does for `ls-tree` (L2731-2733). [https://git-scm.com/docs/git-log]
10. `--diff-filter=A` selects files that are "Added (`A`)". [https://git-scm.com/docs/git-diff]
11. `git rev-parse --git-dir` "print[s] a message to stderr and exit[s] with nonzero status" only when the current directory is not in a Git repository or work tree. So it succeeds in a repo with no commits, and `_anchor_env` does not classify an unborn HEAD as "no git". [https://git-scm.com/docs/git-rev-parse]
12. `--is-shallow-repository`: "When the repository is shallow print "true", otherwise "false"." [https://git-scm.com/docs/git-rev-parse]
13. `git log` in a repo with no commits fails ("does not have any commits yet"). Its exit code is UNVERIFIED (not on the git-log page). This matters only for the "read HEAD once" design (finding 19): if `_anchor_env` stops screening the unborn case, `_rule_seen`'s `log` call fails and gives the git-failed entry. [https://git-scm.com/docs/git-log]
14. `^` with `re.M` "matches at the beginning of the string and at the beginning of each line". `re.search` returns `None` if nothing matches. Both are used at L664 and are not changed by 088. [https://docs.python.org/3/library/re.html]
15. `_git` returns `(r.stdout, r.returncode)`. `returncode` is the "Exit status of the child process. Typically, an exit status of 0 indicates that it ran successfully." [https://docs.python.org/3/library/subprocess.html; repo L1017-1021]

### D. Git calls per pair, counted from the code (finding 2 of the audit)
19. A "pair" is one `_rule_seen(item, step, const)` call. A full read makes 4 wrapper calls: `_git("rev-parse","--verify","-q","HEAD")`, then `_git_ok` for `log`, `ls-tree`, `show` (L643, L649, L656, L661). Early exits: env set → 0; unborn → 1; uncommitted → 2; anchor without RULE_FILE → 3. Each wrapper call starts 2 git processes, `rev-parse --show-toplevel` and then the command (L1014-1018), so a full pair is 8 processes. [repo: scripts/check_pipeline.py]
20. Per item there are up to 3 pairs, not 2. TESTS (05, items ≥ 76, L709-710), SUITE (05, items ≥ 87, L725-738; added by 082 after 03 was written) and VERDICT (06, items ≥ 71, L745-754). Each runs only when its check fires. TESTS and SUITE both anchor on 05, so the `log`/`ls-tree`/`show` for 05 runs twice when both fire; only `const` differs. 03's budget "27 pairs = 54 calls max; 2 pairs = 4 calls on HEAD" (work/084/03-handoff.md L33, L91) counts 2 calls per pair and no SUITE gate, so it is stale on both counts. Corrected from the code: at most 4 wrapper calls × (pairs that fire), with pairs ≤ (VERDICT items ≥ 71 that fire) + (TESTS items ≥ 76 that fire) + (SUITE items ≥ 87 that fire). This matches the audit's "4 per pair ... 8 on HEAD for 083's two pairs". [repo; logs/audit/2026-11-21-084.md]
21. Reading HEAD once: moving `rev-parse --verify -q HEAD` into `_anchor_env` makes 3 per pair plus 1 per run. Caching the 05 anchor (sha + RULE_FILE text) per (item, step) would make the SUITE pair after TESTS cost 0. The census test (L2415-2432) compares `dict(seen)` to GIT_CENSUS exactly. A function with 0 calls is absent from `seen`, so the move means deleting the `("_rule_seen", "_git")` entry, bumping `("_anchor_env", "_git")` from 1 to 2 with a reason, and keeping the total at 47. [repo: tests/test_pipeline_check.py]
22. Design hazard in the move, for R2/R3. Today a non-1 exit from `--verify -q HEAD` gives a per-pair INCOMPLETE entry (exit 1, L646-648). If `_anchor_env` returns an env string for it, `main` prints only `RULE NOT SEEN: not checked (...)` (L1618) and the exit code does not change. A failed git call would then lose its exit 1, which is RI-014's lesson (081: "failed git never 'none'"). Options: env `"unborn HEAD"` only for exit 1, with any other non-zero still loud (an entry or exit 1); or keep the per-pair branch. A moved unborn check also changes what mutation (h) means: with `_anchor_env` screening unborn and the screen removed, `_rule_seen`'s `log` fails and gives a git-failed entry (strict, finding 13). So fixture (h) must pin the exact INCOMPLETE text, or it will not tell "screened" from "git failed". [repo; logs/recurring-issues.md RI-014]
