## 3 ways FOR
1. **Part 1: patch only commit_step's own `subprocess` name, not the global `subprocess.run`. Then no `monkeypatch.context()` scoping is needed and the test's `_g`/`_state` calls are not recorded.** R1 1.6 warns that patching `subprocess.run` also catches the test's own `_g` (tests/test_commit_step.py L29-32). The reason: `cs.subprocess` is the same module object as the test's `subprocess`, so `monkeypatch.setattr(cs.subprocess, "run", rec)` patches it for everyone. Instead, use `monkeypatch.setattr(cs, "subprocess", types.SimpleNamespace(run=rec))`. Why this works: the module `run` looks up `subprocess` as a global each time it is called (scripts/commit_step.py L64). Python docs: "Name resolution of free variables occurs at runtime, not at compile time", and globals are found "by searching the global namespace, i.e. the namespace of the module containing the code block" [https://docs.python.org/3/reference/executionmodel.html]. Grep shows `subprocess` is used only at L45 (import) and L64 in commit_step.py, so a namespace that has only `.run` is enough. This form also reaches main's default `run=run` (R1 1.3), so all 6 T-b rows go through `cs.main([...])` (R1 1.7: 6 of 6). A recorder that appends `args[0]` and then raises makes any git call fail loudly even if the test forgets the `calls == []` assert.
2. **Part 1: add a filesystem check of `.git/objects` as a second assertion. It measures the harm A1 named, not just the call order.** The moved-loop mutant runs `hash-object -w` (L203) and `write-tree` (L205) before it refuses. In the fixture the working log holds L150 and the subject is S150 (tests/test_commit_step.py L48, L275), so `_log_blobs` returns one blob (L138-139). git docs: `-w` will "Actually write the object into the object database" [https://git-scm.com/docs/git-hash-object], and write-tree "Creates a tree object using the current index" [https://git-scm.com/docs/git-write-tree]. Comparing the set of paths under `.git/objects/` before and after (an `os.walk`, no git call) therefore fails under the mutant. It is also independent of the recorder: it keeps the T-b child-process form (`_cli`), so the real argv path is tested end to end. Not run: UNVERIFIED until I2/I3 run the mutant.
3. **Part 2: one parametrized test per constant with literal IDs and `ids=["FROM", "FROM-1"]`. This copies the existing SCRATCH_FROM pin (tests/test_pipeline_check.py L5428) and kills both shift directions with 2 rows.** R1 2.2 explains why tests that read the boundary from the constant (`SF = _cp().SUITE_FROM`, L3680) can never kill a shift. Literal IDs can. The arithmetic (01 "Numbers used"): with the rule "checked iff int(ID) >= FROM", a shift to FROM+1 fails the FROM row and a shift to FROM-1 fails the FROM-1 row. So 2 rows per constant, times the 4 constants with a gap (CHECKLIST, LOG_CHECK, SUITE, VERDICT) = 8 new rows, close the 6 expected survivors (14 − 8 = 6, R1). The helpers already exist with the needed parameters: `_item(..., logged=, verdict=)` (L35-36), `_suite_item(root, suite05, i2=, item=)` (L3658), `_log` (L698). pytest: parametrize lets you "define multiple sets of arguments and fixtures at the test function or class" [https://docs.pytest.org/en/stable/how-to/parametrize.html]. All the fixtures are non-git tmp dirs, so the `_rule_seen` gates return `(None, "")` and need no RULE_FILE setup (R1 2.6).

## 3 ways AGAINST
1. **A literal `assert cp.<NAME> == <N>` in each row (R1 2.10's last line) hides whether the behavior rows pin anything.** Each shift mutant would then be killed by the value assert first, in every row. The mutant run would print "killed" even if the fixture never reaches the gate. That is the RI-001 trap of a kill that is asserted but not measured. TIMED_FROM shows it today: `== 90` (L4405) is its only FROM-side kill and there is no behavior pin at literal 090 (R1 2.3). Fix: put the value asserts in one separate test (e.g. `test_from_values`), and have I2/I3 record which behavior test fails for each of the 14 shifts. When run with the value test deselected, each shift should still fail a behavior row. (Reasoning chain, not run.)
2. **Shift mutants alone leave per-site gates unpinned.** That makes "pinned" true only for the shift mutant class. A shift changes every gate site at once (R1 2.8), so one pair per constant kills it. An operator or site mutant (`>=` -> `>`, or one site rewritten to a literal) is a different class. Site counts from check_pipeline.py: LOG_CHECK_FROM 3 (L1049, L1385, L1507), TESTS_FORMAT_FROM 3 (L811, L824, L1066), TIMED_FROM 4 (L814, L827, L1055, L1087). That is 10 sites, against the 3 behavior pins these constants would get. Example: R1's LOG_CHECK pin goes through the INCOMPLETE gate L1049. A `>` mutant at L1385 (LOG TIME) or L1507 (LOG BATCH) would not touch it. Pinning every site would cost about 14 operator mutants plus fixtures for LOG TIME/LOG BATCH, which need git. That is beyond what the request asks for ("a FROM-1 shift per constant", request "Done looks like"). Recommend keeping it out of scope and listing it as a residual, not claiming the cutoffs are "fully pinned".
3. **Part 1's in-process form has its own blind spots and costs, so it must be added beside T-b, not replace it.** (a) `cs.main([...])` skips the `if __name__ == "__main__": sys.exit(main(...))` path (L247-248) and real argv decoding, so the CR/LF rows travel as Python strings, not process arguments. T-b's `_cli` keeps that coverage. (b) The no-value row is refused in `main` before `commit` is called (L235-238), so `calls == []` holds for it under any reordering inside `commit`. That row cannot kill the moved-loop mutant; only the 5 `_trailer_ok` rows can. Counting "6 of 6 kill" would overstate it (correct: 5 rows kill, 1 row is a guard). (c) Replacing `cs.subprocess` also breaks `run`'s `FileNotFoundError` branch semantics for that test only. That is harmless here, but a recorder must not return `None`, or commit raises "no git" (L162-163) and hides an order bug as a different refusal. Raising from the recorder avoids this. (Reasoning from scripts/commit_step.py L61-67, L156-163, L233-244.)
