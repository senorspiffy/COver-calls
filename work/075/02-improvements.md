## 3 ways FOR
1. **Fail closed on every entry the parser cannot read. This bug class is real outside this repo too.** R1's Open question 1 (a)-(f) closes A1's x4/x5 cases. That means: brackets on one line only, comma split at paren depth 0, one pair of matching quotes stripped, every entry checked against a pattern, empty lists rejected, duplicate keys rejected. A published Rust linter for Claude Code agent files (roba 0.7.1, `agent_check.rs`) has exactly the same bug. Its comment reads "Inline list: `tools: Read, Edit, Write`", followed by `.split(',')` and `.trim()`. The WebFetch reader concluded "`tools: [Read, Edit]` would yield `"[Read"` and `"Edit]"`" and that unknown entries "are not rejected" [https://docs.rs/crate/roba/0.7.1/source/src/agent_check.rs]. So a comma-split parser that accepts any token is a common mistake, not a one-off, and the guard is to reject anything unparsed. The docs give both forms in English, Chinese and Spanish ("como una cadena separada por comas como `Read, Grep, Bash` o una lista YAML" [https://code.claude.com/docs/es/sub-agents.md]), so the flow form is in scope, as the request says.
2. **Pin an allow-list for the no-shell agents instead of a list of shell tools. This is the strongest single change.** All 4 no-shell files have the same 6 tools (above). Proposal: `NO_SHELL_ALLOWED = {Read, Write, Glob, Grep, WebSearch, WebFetch}`, and each NO_SHELL stem's parsed set must be a subset of it, compared case-sensitively by exact name. That one check catches every way a command could get in:
   - `Bash`, `bash`, `Bash]` and `"Bash"`, whether the parser got it right or not.
   - Monitor. The Japanese docs say "Monitor がコマンドを実行する場合、Bash と同じ権限ルールを使用する" (when Monitor runs a command it uses the same permission rules as Bash) [https://code.claude.com/docs/ja/tools-reference.md].
   - PowerShell.
   - `Agent`/`Task`. The Chinese docs say that in a subagent definition the type list in `Agent(...)` "括号内的任何类型列表都会被忽略" (any type list inside the parentheses is ignored) [https://code.claude.com/docs/zh-CN/sub-agents.md]. So `Agent(worker)` on r1 is unrestricted spawning, including general-purpose, which has every tool (R1 F23).
   - `Skill`, every `mcp__*` entry, and any tool Claude Code adds later.

   This makes R1 Open question 2 (the MCP pattern) and question 3 (the shell-name set) moot for the agents that matter. Shell agents (i2, i3, a1) need only the parse check. A wider tool on a no-shell agent becomes a visible test edit, which is the RULES decision the 072 set assert was meant to force. Two sources make the same point. French: "Le champ `tools` est votre frontière d'isolation" (the tools field is your isolation boundary) [https://www.glukhov.org/fr/ai-devtools/claude-code/claude-code-subagents/] (WebFetch). Turkish: the only rule that holds is "orada olmayan bir araç" (a tool that isn't there) [https://agentsroom.dev/tr/blog/read-only-review-agent] (WebFetch).
3. **Match the ways Claude Code itself fails silently, so each one shows up as a test error.** The Chinese docs: "Claude Code 会忽略无法识别的字段，且不报告错误" (Claude Code ignores unrecognised fields and reports no error) [https://code.claude.com/docs/zh-CN/sub-agents.md]. So a mis-cased `Tools: Read` makes Claude Code see no `tools` at all, and the agent inherits every tool, Bash included (R1 F7). The current `_field` uses an exact `startswith("tools:")`, so it already reports "no tools: line" for this. Pin it with a fixture (`Tools: Read` → error), so a later "case-insensitive key" tidy-up cannot turn it into a pass. Do the same for a duplicate `tools:` key (R1 Open question 1(f) → error) and a misspelled `disallowedtools:`. The misspelled key is ignored by Claude Code and also ignored by the test, which is consistent; a fixture should show that it removes nothing.

## 3 ways AGAINST
1. **A hand-written YAML subset is a second parser, and it can disagree with Claude Code's.** YAML has more ways to write a value than R1's forms (a)-(f) cover: flow lists over several lines, block scalars (`>`, `|`), anchors, tags, a whole value in quotes (`tools: 'Read, Bash'`), and comments (R1 F11-F13; [https://yaml.org/spec/1.2.2/]). PyYAML cannot be used without a new dependency (R1 F6). Two Claude Code issue titles found in this search suggest the runtime's own array handling has changed between versions: "[BUG] Sub-agent frontmatter `tools:` array silently drops first and last positions at spawn time" (#60237) and "[BUG] Sub-agent tool inheritance drops first/last array elements" (#14580) [https://claudeissues.com/issue/60237-bug-sub-agent-frontmatter-tools-array-silently-drops-first-and-last-positions-at]. The page body could not be fetched (robots_disallowed), so the content and the versions are UNVERIFIED. The cost: whichever way the parser leans, it is a guess about the runtime. It must therefore refuse anything outside a small known subset, and accept false errors on valid YAML, for example a whole-value-quoted list, rather than try to cover all of YAML.
2. **The test is a lint on files. It does not enforce anything, so it should not grow beyond the request.** It cannot prove what Claude Code grants (R1 F10 and F18 are UNVERIFIED by a run). The Russian docs add that when the YAML does not parse, Claude Code "не читает никакие поля из файла, пропускает его" (reads no fields from the file and skips it) [https://code.claude.com/docs/ru/sub-agents]. So the runtime and the test can each go wrong in their own way. Two sources warn that a tool list is not a sandbox. French: "L'isolation est une liste d'outils autorisés, pas un sandbox." (isolation is an allow-list of tools, not a sandbox) [https://www.glukhov.org/fr/ai-devtools/claude-code/claude-code-subagents/] (WebFetch). Turkish: "bir `bash -c` araç yasak listesinin etrafından dolaşır" (a `bash -c` goes around a tool deny-list) [https://agentsroom.dev/tr/blog/read-only-review-agent] (WebFetch). The point for this item: keep 075 to the parser, the fixtures and (FOR 2) the allow-list. Leave the optional wording regex (R1 Open question 5) out, or mark it optional. It stays a gameable text lint either way, and A1 rated it not worth an item.
3. **A list of tool names goes out of date, and the request's pattern already fails documented forms.** The pattern `^[A-Za-z]+(\(.*\))?$` rejects all 5 documented MCP forms (R1 F15). It also lets `Bash) (x` through, because `.*` is greedy. The docs carry many version notes: Task was renamed Agent in 2.1.63 (R1 F16), and the zh-CN page cites versions from v2.1.172 to v2.1.296 for subagent behaviour [https://code.claude.com/docs/zh-CN/sub-agents.md]. A hard-coded set of shell tool names (R1 Open question 3) will miss the next tool that can run a command. If FOR 2 is not adopted, this item ends up maintaining two lists, a pattern and a shell set, and each can drift. That is the cost of R1's Open questions 2 and 3 as written. FOR 2's allow-list needs only the pattern for shell agents. There, a failing MCP entry is a loud false error and grants nothing.

## Holes to watch out for (summary)
1. **Base the no-shell check on the allow-list, not on "is Bash present?"** (FOR 2). Monitor, PowerShell, `Agent`/`Task` (the parenthesised list is ignored in subagents), `Skill` and `mcp__*` each give a no-shell agent a way to run commands, or reach an agent that can. Fixture n: `tools: Read, Monitor` on a NO_SHELL stem → fails. Mutation: allow-list check replaced by `"Bash" in tools` → n fails.
2. **A whole value in quotes** (`tools: 'Read, Bash'`) is valid YAML, and as a comma string it may grant Bash. Under R1's (c) it splits into `'Read` and `Bash'`, which fail the pattern → error. That is acceptable, but add it as a fixture so nobody "fixes" it into a pass.
3. **Mis-cased or misspelled keys** (`Tools:`, `disallowedtools:`) are ignored by Claude Code with no error (zh docs). `Tools:` → the agent inherits everything. Keep the exact-case key match, and pin `Tools: Read` → "no tools: line".
4. **Greedy `(\(.*\))?`** lets `Bash) (x` pass. Use `\([^()]*\)` (R1 Open question 2). After the depth-0 split, a stray `)` must be an error.
5. **Flow lists over several lines and block scalars** (`>`, `|`): refuse them (R1 (a)). Their runtime handling is UNVERIFIED, and issue titles #60237 and #14580 suggest array handling has varied across Claude Code versions (content UNVERIFIED).
6. **Duplicate `tools:` keys**: which one the runtime uses is UNVERIFIED (R1 F19), so refuse them.
7. **Translations lag**: the ru `tools` row leaves out the format sentence. Cite the English page for the accepted forms (R1 F7).
8. **A lint, not a boundary** (AGAINST 2): do not describe this test as making the agents safe. It makes a change to their tools visible.
9. **Scope**: leave the wording regex out, or mark it optional (A1: "not on its own worth an item"). 076, 077 and 079 touch scripts/check_pipeline.py, not this test, so no file overlap is known (brief).
