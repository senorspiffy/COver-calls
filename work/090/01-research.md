### (A) Untimed and sent-back items (RI-010)
- A1. The I2 format is `rf"\d+ files? changed \| tests {_STATS}{_TAIL}"` (L384). `_TAIL = r"(?: in \d+\.\d+(?:s| seconds)(?: \(\d+:\d{2}:\d{2}\))?)?(?: \(.*\))?"` (L324): the whole ` in <s>s` part is inside `(?:...)?`. So `log_fields_ok` (L567-575, `re.fullmatch`) accepts a field with no time. `?` "Causes the resulting RE to match 0 or 1 repetitions of the preceding RE", and fullmatch returns a Match "If the whole string matches" [https://docs.python.org/3/library/re.html]. This confirms A1's probe (`'1 file changed | tests 5 passed'` -> True, 086 audit L59). [repo L324, L384, L567-575]

The I2 field is "the last line of `python3 -m pytest -q`" (docstring L91-92). So requiring ` in <s>s` costs a correct I2 nothing. ### (B) Shallow clones (RI-014)
- B1. The shallow file "lists commit object names and tells Git to pretend as if they are root commits (e.g. "git log" traversal stops after showing them ...)". "Shallow commits do have parents, but not in the shallow repo, and therefore grafts are introduced pretending that these commits have no parents." [https://git-scm.com/docs/shallow]
- B2. So the shallow view only removes parent edges (079/01 F7). Anything reachable in the shallow view is reachable in the full clone, but not the other way round. This is the basis for B5, B8 and B10 (derived, UNVERIFIED by probe) [https://git-scm.com/docs/shallow].
- B3. `--is-shallow-repository`: "When the repository is shallow print "true", otherwise "false"." `--git-common-dir`: "Show `$GIT_COMMON_DIR` if defined, else `$GIT_DIR`." [https://git-scm.com/docs/git-rev-parse]. The code already has `_shallow_boundaries()` (L1183-1202) and `_anchor_env()` (L623-632). `_anchor_env()` returns `"shallow clone; run git fetch --unshallow"` for boundaries or "unreadable", and main() computes it once as `env` (L1535). The three readers can share that value. [repo L623-632, L1183-1202, L1535]
- B4. `git fetch --unshallow`: "If the source repository is shallow, fetch as much as possible so that the current repository has the same history as the source repository." So after the hint the clone can still be shallow, and the check must test again [https://git-scm.com/docs/git-fetch]. run-item.md L12 already says so, but it lists only UNTRACKED CHANGE, RESEARCH CODE and REAL-DATA FIELD. [repo .claude/commands/run-item.md L12]
- B5. LOG TIME (`late_log_lines`, L841-874) blames each committed log file and compares each line's stamp with `committer-time` (L857-872). It never asks about shallowness. git-blame: `--root` "Do not treat root commits as boundaries", so by default root commits are boundaries [https://git-scm.com/docs/git-blame]. In blame.c's porcelain output, `boundary` is printed `if (suspect->commit->object.flags & UNINTERESTING)`, and `committer-time` is printed for each commit [https://code.googlesource.com/git/+/HEAD/builtin/blame.c]. That a shallow commit gets that flag (as a pretend root, B1) is not shown in either source: UNVERIFIED. A1 observed it in practice: in a `--depth 1` clone, "blame gives every line the boundary commit's time", and a late line read `LOG TIME: none` where the full clone flags it (logs/audit/2026-11-21-081.md L99).
- B6. Direction of the LOG TIME error: a line that blame gives to a shallow boundary B is really from B or one of B's hidden ancestors. B's committer time is usually later, so `stated > commit` (L870) becomes false and a late line is missed (a silent pass, RI-002 shape). A line blamed to a non-boundary commit C has C's real parents in the shallow view (grafts are only on listed commits, B1), so its attribution is the same as in the full clone. [derived from B1; UNVERIFIED by probe]
- B7. MAIN AHEAD (`main_ahead`, L1416-1434) runs `rev-list --count HEAD..<origin/main sha>`. `A..B` is "^A B", meaning commits "reachable from" B "but not from" A [https://git-scm.com/docs/git-rev-list]. The fetched page does not document `--count` (it appears only in the `--missing-only` text): UNVERIFIED from the docs. The code relies on it already (081).
- B8. Direction of the MAIN AHEAD error (from B2): if the shallow count is 0, origin/main's tip is reachable from HEAD in the shallow view, so it is in the full clone too, and the full count is also 0. A positive count can be false: HEAD's path to main's tip may run through a missing parent. A1 saw exactly this: a false "1 commits not in HEAD" where the full clone has no line (081 audit L100). Only a positive answer is uncertain. [derived from B1, B2]
- B9. `main_ahead()` is also called inside `open_branches` (L1051). Its result `behind` drops origin/main and every ref passing `merge-base --is-ancestor ref MAIN` (L1057). A false positive therefore also removes origin/main from OPEN BRANCHES (081 audit L100). `--is-ancestor` "exit with status 0 if true, or with status 1 if not" [https://git-scm.com/docs/git-merge-base]. In the shallow view, 1 is uncertain and 0 is exact (B2). [repo L1051, L1057]
- B10. Unrelated test (`open_branches` L1061-1072): `merge-base --all HEAD ref` exit 1 makes the ref "no common history", not scanned, plus a BRANCH ERROR when it holds checked paths. `--all`: "Output all merge bases for the commits, instead of just one" [https://git-scm.com/docs/git-merge-base]. That page does not document the exit status for no common ancestor: UNVERIFIED from the docs. A1 observed exit 1 with no output on git 2.43 (081 audit L10). From B2, exit 1 in a shallow clone is uncertain (A1: a branch that shares history in the full clone, 081 audit L61-63). Exit 0 proves a common ancestor, but the shallow bases may not be the full clone's best bases. The merge-tree result and `changed()` (L1073-1092) can then differ too: UNVERIFIED, not probed (Open question 4).
- B11. `git clone --depth` "Implies `--single-branch` unless `--no-single-branch` is given". With a single branch, "Further fetches ... will only update the remote-tracking branch for the branch this option was used for" [https://git-scm.com/docs/git-clone]. In a default `--depth 1` clone, `git branch -r` would then list only that branch. OPEN BRANCHES would say none and `--next-id` (L1437-1451) would ignore open branches' IDs (RI-009). This is a cut set of refs, not cut history, and it is outside the request. A1's probe used `--no-single-branch` (081 audit L61). Whether the checker can detect it (e.g. from `remote.origin.fetch`) is UNVERIFIED (Open question 5).
- B12. Existing fixtures already build depth-1 clones with `git clone -q --depth 1 file://<repo>` and assert `--is-shallow-repository` == "true" (tests/test_pipeline_check.py L947-957, L1053-1065). The new fixture needs `--no-single-branch` for origin/main and the branch refs (B11). It also needs a pinned committer time so that the tip commit's time is not before the late line's stamp: A1's `lt`/`lt1` used a line timed 23:59, committed 01:30, with a later commit on top (081 audit L99). [repo tests L947-957, L1053-1065]
