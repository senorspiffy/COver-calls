## Question
For a ~$3k Webull (US) covered-call account, the person wants (1) a backtester, (2) a paper-trading bot, and (3) later, maybe, live trading through Webull's official API. This brief answers:
1. What does Webull's **official** OpenAPI allow for US options: orders, chains/quotes/greeks, paper trading, access requirements, rate limits, SDKs? Are unofficial libraries risky?
2. Where can we get historical option data with bid/ask for a backtest, cheaply? If we can't, how good is a Black-Scholes model driven by a volatility proxy plus a spread assumption?
3. What is the evidence for the person's timing ideas: "sell into strength" (sell calls after up days), day-of-week effects, IV-rank/percentile entry, and weekly vs monthly?
4. What does research say about ML or "learning" bots for timing options, and which adaptive approaches are realistic and testable?
5. Which ETFs priced ≤ $28 have options liquid enough for 001's screen (spread ≤ $0.05, OI ≥ 500)?

## Findings (one claim per line, each with [source URL] or UNVERIFIED)

### A. Webull official OpenAPI (US)
- A1. Webull's developer site offers a Trading API for "equities, options, futures, crypto, and event contracts", plus a Market Data API, a Broker API, a Connect API and an SDK with a "ready-to-use test account". [https://developer.webull.com/apis/home]
- A2. For the US, the Trading API overview lists "Options: Single-leg and multi-leg strategies". [https://developer.webull.com/apis/docs/trade-api/overview.md]
- A3. Options strategies in the API include `SINGLE` and `COVERED_STOCK` ("covered call or buy-write"), plus VERTICAL, CALENDAR, DIAGONAL, COLLAR_WITH_STOCK, and others. Time in force is DAY or GTC only. `TRAILING_STOP_LOSS` is not supported for options. [https://developer.webull.com/apis/docs/trade-api/options.md]
- A4. **Webull's own pages contradict each other.** The options page lists MARKET, LIMIT, STOP_LOSS and STOP_LOSS_LIMIT orders [https://developer.webull.com/apis/docs/trade-api/options.md]. The Trading API FAQ says "Options do not support `MARKET` or `TRAILING_STOP_LOSS` order types" and "Options sell-side orders only support `DAY` as time in force (`GTC` is buy-side only)". [https://developer.webull.com/apis/docs/trade-api/faq.md] We plan for the stricter rule: every sell-to-open is a DAY limit order, and GTC is used only for buy-to-close. That still fits 001 step 6 (GTC buy-to-close at 50%).
- A5. The FAQ says trading agreements are required, "especially for options". It does not say which options level the API needs. [https://developer.webull.com/apis/docs/trade-api/faq.md] We assume the account's normal options level (001: Level 1 covers covered calls and CSPs) also applies through the API. UNVERIFIED.
- A6. Option market data: the Option Snapshot endpoint returns bid, ask, bid/ask size, last, volume, `open_interest`, `imp_vol`, delta, gamma, theta, vega, rho and strike. It takes at most "20 symbols per query" and only `US_OPTION`. You must pass OCC-style symbols (e.g., `AAPL260522C00300000`). [https://developer.webull.com/apis/docs/reference/option-snapshot.md]
- A7. We found **no option-chain, expiration-list or strike-list endpoint** in Webull's docs index. The index lists only Option Snapshot, Option Tick and Option Historical Bars. [https://developer.webull.com/apis/llms.txt] So the bot may have to build contract symbols itself, from the expiration calendar and a strike grid. UNVERIFIED that no chain endpoint exists; ask trading.api@webull-us.com (contact listed in the FAQ).
- A8. Option Historical Bars return OHLCV only, with no bid/ask, at most 1,200 bars per call. The page does not say whether expired contracts are covered. [https://developer.webull.com/apis/docs/reference/option-historical-bars.md] That is not enough for a bid/ask-accurate backtest.
- A9. Options data needs a market-data entitlement. To get options last sale and quotes you must "Subscribe OPRA Real-Time Non-display". The page gives no price. [https://developer.webull.com/apis/docs/market-data-api/overview.md] Subscriptions bought in the Webull app or desktop "are independent of OpenAPI", so a separate OpenAPI subscription is needed. [https://developer.webull.com/apis/docs/market-data-api/faq.md] Price: UNVERIFIED.
- A10. Rate limits: Market Data HTTP allows "300 requests per 60 seconds" [https://developer.webull.com/apis/docs/market-data-api/faq.md]. On the Trading side, Place, Replace and Cancel Order each allow 600/60s, Preview Order 150/10s, Account Balance and Positions 2/2s, and Account List 10/30s. [https://developer.webull.com/apis/docs/trade-api/overview.md] A once-a-day scan of one or two tickers uses a tiny share of this.
- A11. Paper trading: Webull calls it a "Sandbox (paper trading)". You apply from [My Application] in the Developer Management Center. The sandbox is approved automatically, "usually within a few minutes". Production API review takes "1 to 2" working days, and you must already have an account in your own name. [https://developer.webull.com/apis/docs/authentication/IndividualApplicationAPI.md] Sandbox hosts include `api.sandbox.webull.com`. [https://developer.webull.com/apis/docs/sdk.md]
- A12. In the sandbox, paid market data is "15-minute delayed data by default". [https://developer.webull.com/apis/docs/market-data-api/faq.md]
- A13. No minimum balance for API access is stated on these pages (UNVERIFIED either way). The API has "no extra charges", and "Trading fees are the same as those in the Webull App". Individual developers need no IP whitelist. [https://developer.webull.com/apis/docs/faq.md]
- A14. There are two official SDKs: Python (`webull-openapi-python-sdk`, Python 3.8–3.14) and Java (`com.webull.openapi:webull-openapi-java-sdk`, JDK 8+). [https://developer.webull.com/apis/docs/sdk.md] The SDK README names Webull US among its supported regions. [https://github.com/webull-inc/webull-openapi-python-sdk] Authentication uses an App Key and App Secret with HMAC-SHA1 signatures, plus a token step with 2FA. [https://developer.webull.com/apis/llms.txt]
- A15. **Unofficial library risk.** The PyPI package `webull` calls itself "The unofficial python interface for the WeBull API". Its latest release is 0.6.1 (10 Jan 2023), and it warns: "Webull may update the APIs or the endpoints at any time." [https://pypi.org/project/webull/] Webull's Terms of Service forbid access "through any means not intentionally made available by Webull for your specific use" and forbid reverse engineering "without authorization". [https://www.webull.com/protocol/webull_terms_of_service] Verdict: use only the official SDK. Do not use reverse-engineered libraries.

### B. Historical option data for backtesting
- B1. ORATS Near-EOD: NBBO bid/ask, greeks and IVs, back to 2007 including delisted symbols. The history backfill is a one-time **$599**; daily data is $99/month. [https://orats.com/near-eod-data]
- B2. Cboe DataShop "Option Quotes End of Day with Calcs": 15:45 ET NBBO bid/ask for every series from January 2012. IV and greeks cost extra (Calcs add-on). The page shows no price, but a free sample download is available. [https://datashop.cboe.com/option-quotes-end-of-day-with-calcs] Price: UNVERIFIED.
- B3. ThetaData: the FREE tier gives EOD options data from 2023-06-01 but **no bid/ask quote endpoints**. Bid/ask history starts on paid tiers: VALUE from 2020-01-01, STANDARD from 2016, PRO from 2012-06-01. The page shows no prices, and it states the free limit as both 30 and 20 requests/min. [https://thetadata.net/docs/Articles/Getting-Started/Subscriptions.html]
- B4. Massive: Options Basic is $0 with 2 years of history. Starter is $29/mo (2 yr), Developer $79/mo (4 yr), Advanced $199/mo (5+ yr, the only plan that lists "Quotes"). The page does not say that historical bid/ask is included. [https://massive.com/options] That Massive is the former Polygon.io is UNVERIFIED (none of the Massive pages we opened say so).
- B5. yfinance "is **not** affiliated, endorsed, or vetted by Yahoo", and Yahoo's API "is intended for personal use only". Latest version is 1.7.0 (26 Aug 2026). [https://pypi.org/project/yfinance/] The claim that it returns only *current* chains, not history, is UNVERIFIED from docs; the PyPI page doesn't cover options.
- B6. **Sandbox fact (tested today):** from this repo's container, Yahoo (yfinance), stooq and `cdn.cboe.com` were all refused by the outbound proxy (HTTP 403 CONNECT). Only the WebFetch tool reached Cboe's delayed-quote JSON. So the backtester must run on **checked-in or offline data**, and its tests must not depend on network access. [tested: `curl` and yfinance 1.7.0 in scratchpad venv, 2026-10-30 18:0x UTC]
- B7. Cboe publishes free daily VIX closing values from 1990, plus other indices (VIX9D, VVIX, OVX, GVZ, VXEEM, VXAPL, VXAZN). [https://www.cboe.com/en/tradable-products/vix/vix-historical-data]
- B8. VIX gives "constant, 30-day expected volatility of the S&P 500" from SPX options about 23–37 days out. Cboe puts the average implied-minus-realized premium at about 3–4 points. [https://www.cboe.com/insights/posts/what-the-vix-and-vix-1-d-indices-attempt-to-measure-and-how-they-differ]
- B9. Black-Scholes assumes constant, known volatility, no dividends, European exercise, and zero transaction costs (no spread). [https://www.macroption.com/black-scholes-assumptions/] Original paper: Black & Scholes, J. Political Economy 81(3), 1973. [https://macroption.com/the-pricing-of-options-and-corporate-liabilities]
- B10. Equity skew is usually a "smirk": OTM puts carry higher IV than OTM calls. [https://www.optionseducation.org/news/volatility-skew-and-options-an-overview] Our inference (UNVERIFIED as a number): a 0.30Δ OTM call usually has lower IV than VIX-like ATM/wing-weighted vol. Pricing it at VIX therefore likely **overstates** the premium we would collect.
- B11. **Fallback model and its limits** (method, built from B7–B10). Price each call with BS(S, K, T, r, q, σ) where σ = VIX/100 × k, and k is calibrated, not assumed. Then subtract half of an assumed spread on each fill (001 cost table). Known gaps:
  - VIX covers only the S&P 500, so it is a poor proxy for KWEB, BITO or JETS (B7 lists no index for them).
  - It ignores skew (B10) and early exercise before ex-dividend (001 F3).
  - Spread in a crisis is wider than any constant.
  - Results are only as good as the calibration. Calibrate k and the spread on real quotes: either a few months of our own logged Webull/Cboe snapshots, or one purchased sample (ORATS $599 backfill, or a Cboe DataShop sample file).
  - Label every modelled result "MODELLED, not market prices".

### C. Timing ideas
- C1. **Leverage effect:** "volatility increases when the stock price falls" (and the reverse). This holds for implied and realized vol. [https://archive.nyu.edu/jspui/bitstream/2451/26702/2/FIN-00-037.pdf] (Figlewski & Wang, 2000). Inference: after an up day, IV tends to be a bit *lower*, so a fixed-delta call pays less. The strike sits higher, though, so assignment below cost basis is less likely. This is a trade-off, not a free edge.
- C2. **"Sell into strength": no primary evidence found.** tastylive has episodes titled "Selling Calls Multiple Up Days" (2017-01-12) and "Short Calls Contrarian Entries" (2016-09-29), but both pages load only as show landing pages, with no data. [https://www.tastylive.com/shows/market-measures/episodes/selling-calls-multiple-up-days-01-12-2017] [https://tastylive.com/shows/market-measures/episodes/short-calls-contrarian-entries-09-29-2016] → UNVERIFIED; the backtester must test it.
- C3. **Weekend effect:** "option returns are significantly lower over nontrading periods, the vast majority of which are weekends". The authors call this persistent mispricing, not risk. [https://ideas.repec.org/a/bla/jfinan/v73y2018i2p861-900.html] (Jones & Shemesh, J. Finance 2018). Inference: option *sellers* gain when holding short options over weekends. For a 30–45 DTE call, which spans 4–6 weekends whatever day it is opened, the entry weekday probably matters little. UNVERIFIED; test it.
- C4. **This source disagrees.** OptionMetrics found long-strangle returns on 5 large stocks (AAPL, AMZN, MSFT, GOOGL, TSLA) were **highest on Monday** and lowest on Friday. The study used OTM options > $0.20 with > 1 week to expiry, and no period is stated. [https://optionmetrics.com/blog/2022_examining_anomalies_what_is_the_best_day_to_buy_stocks_and_options/] It doesn't say how a "Monday return" is measured, so it can't be squared with C3. It is also about long strangles on single stocks, not short calls on ETFs. Weak evidence either way.
- C5. **IV percentile entry:** ORATS' covered-call backtest found the best results with IV percentile > 66%, 30 DTE, avoiding earnings, and holding to expiry. [https://orats.com/blog/covered-call-backtest-finding-the-best-maturity-strike-iv-and-earnings-methods] (verified in 001, R2 FOR1/FOR2). The test covered 16 stocks and ~3.5M combinations, so this is also the best of many tries; see D3.
- C6. **Weekly vs monthly (gross):** in a Cboe-sponsored study through 2015, the weekly SPX PutWrite (WPUT) collected 39.3%/yr gross premium vs 24.1% for monthly PUT (2006–2015). WPUT had lower std dev over 10 years and a max drawdown of 24.2% vs PUT 32.7%. [https://ir.cboe.com/news/news-details/2016/New-Study-On-Weekly-Monthly-SP-500-PutWrite-Indexes-Released-01-27-2016/default.aspx] Caveats: puts not calls, SPX index options not a ≤$28 ETF, gross of spreads, and the release gives no WPUT compound return. Together with 001 C3 (4 weekly SPY calls ≈ 92% more premium) and 001's spread table, the extra weekly premium is real but must beat about 4× the spread cost.

### D. ML / "learning" bots
- D1. ML does predict stock returns a little, but only a little. In Gu, Kelly & Xiu, trees and neural nets reach monthly out-of-sample R² of "0.33% and 0.40%" for single stocks and "1.08% to 1.80%" for the S&P 500 built bottom-up. The useful signals were momentum, liquidity and volatility. [https://www.nber.org/papers/w25398.pdf] [https://nber.org/papers/w25398]
- D2. Bali, Beckmeyer, Moerke & Weigert (RFS 2023) found nonlinear ML predicts equity-option returns well enough for long-short profits "even after accounting for transaction costs". They used more than 12 million observations from 1996–2020. [https://www.wiwi.uni-muenster.de/fcm/en/publication/98329575] This is a cross-sectional, long-short, many-stock result. It is not evidence for timing short calls on one ETF with ~12 trades a year.
- D3. Backtest overfitting: "Standard statistical techniques designed to prevent regression over-fitting … tend to be unreliable" for strategy backtests. The paper proposes measuring the probability of backtest overfitting (PBO). [https://papers.ssrn.com/abstract=2326253] (Bailey, Borwein, López de Prado, Zhu, J. Computational Finance).
- D4. Sample size (our math, see Numbers): a monthly strategy on one ETF over 10 years gives about 120 trades. That is far too few to fit an ML model with many inputs; with tens of features it will overfit. Realistic "adaptive" methods that we *can* test:
  - (a) rule filters with one or two parameters, such as IV percentile above a threshold (C5), trend or up-day filters (C1/C2), or skipping an entry when the spread is too wide;
  - (b) walk-forward selection: pick the parameter on years 1..n and trade year n+1;
  - (c) a fixed, pre-registered list of variants, with every variant tested reported (not just the winner), and a held-out final period;
  - (d) a simple bandit or "pick the best of N rules on trailing data" learner, compared against the fixed rule.
  
  That (d) helps here is UNVERIFIED; no source found.

## Numbers used (show the math)
- Rate-limit headroom: a daily scan of 2 tickers × ~6 expiries × ~10 strikes = 120 option symbols ÷ 20 per snapshot call = **6 calls**. The limit is 300/60s (A6, A10), so that uses **2%** of one minute's allowance.
- KWEB position: 100 × $23.7 = **$2,370** ≤ $3,000 − $200 buffer ✓. JETS: 100 × $26.70 = $2,670 ✓. BITO: 200 × $11.15 = $2,230 (2 contracts) ✓. UNG: 300 × $9.00 = $2,700 (3 contracts) ✓. EWZ: 100 × $32.5 = $3,250 ✗. FXI: $3,300 ✗.
- Spread drag at KWEB's 25C spread ($0.01): $0.01/2 × 100 = $0.50 per fill. At 24.5C ($0.06): $3.00 per fill. Monthly hold-to-expiry, 12 fills/yr: $6 vs $36 = 0.2% vs 1.2% of $3,000. Weekly hold, 52 fills: $26 vs $156 = 0.9% vs 5.2%.
- Weekly vs monthly gross premium (C6): 39.3 / 24.1 − 1 = **63%** more gross premium for weekly SPX puts, 2006–2015.
- ML sample size (D4): 10 yr × 12 monthly trades = **120** trades. Weekly gives 10 × 52 = 520, still small and strongly correlated with each other. Gu-Kelly-Xiu's best monthly single-stock R² of 0.40% (D1) means about 99.6% of monthly return variance is left unexplained.
- VRP (B8): VIX averaged ~23 vs realized ~24 in 2022, so implied was **below** realized that year. That is why a fixed "VIX = what sellers earn" assumption is unsafe; calibrate k (B11).

## Fit for a ~$3k account
- **Webull API:** fine for a later live phase. Use the official Python SDK, the free API, and the paper sandbox. Watch out for: (1) a separate paid OPRA OpenAPI entitlement for real-time options data (price UNVERIFIED); the sandbox gets 15-min delayed data; (2) no confirmed chain endpoint, so the bot builds OCC symbols itself; (3) selling calls is DAY-limit only (A4). Phase 3 stays research-only, as the request says.
- **Backtester:** with $0 of data, the only bid/ask-free route is the BS + VIX-proxy model (B11). Its results must be labelled MODELLED, and the spread is a parameter swept from $0.01 to $0.10. The cheapest *real* bid/ask history is a one-time ORATS $599 backfill (B1), about 20% of the account; not recommended now. Suggest the paper bot log real Webull snapshots daily, so the model can be calibrated later at no cost.
- **Environment:** market-data sites are blocked from this container (B6). Ship a small checked-in sample dataset (e.g., VIX and the ETF's daily closes, once the person downloads them) and make every test run offline.
- **Ticker choice:** this is the biggest change from 001. No broad ETF ≤ $28 passes the liquidity screen (E2). The options are: (a) accept a volatile sector or country ETF like KWEB, which has more premium and more risk; it is concentrated China exposure, and 001 F4 asks "would you hold it a year anyway?"; (b) wait until ~$3.3k+ for EWZ or FXI (also single-country), or ~$5.6k+ for broader names; (c) the wheel or a covered-call ETF (001 alternatives 1 and 2). BITO and UNG track futures and are very volatile; flag them as unsuitable "income" underlyings (house view, not sourced).
- **Timing ideas:** none has solid evidence for 30–45 DTE ETF covered calls. Run each as a pre-registered backtest variant, alongside 001's baseline: up-day entry, weekday entry, IV-percentile filter, weekly cadence. Report all of them, net of spread and fees.
- **"Learning" bot:** full ML is not justified with about 120 trades (D3, D4). Simple filters with walk-forward selection and a fixed, fully reported list of variants are the honest version of "adaptive".
- Taxes and assignment are unchanged from 001: short-term ordinary income, and early-exercise risk around ex-dividend dates.
