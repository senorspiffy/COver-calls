### C. Git: what a worktree shares
- C1. "In general, all pseudo refs are per-worktree and all refs starting with `refs/` are shared ... There are exceptions, however: refs inside `refs/bisect`, `refs/worktree` and `refs/rewritten` are not shared." [https://git-scm.com/docs/git-worktree]
- C2. In a linked worktree, `$GIT_COMMON_DIR` points back to the main worktree's `$GIT_DIR`, and `refs/heads/...` resolve there "since refs are shared across all worktrees, except `refs/bisect`, `refs/worktree` and `refs/rewritten`". [https://git-scm.com/docs/git-worktree]
- C3. "The latest stash you created is stored in `refs/stash`; older stashes are found in the reflog of this reference". refs/stash is under `refs/` and is not one of the three exceptions, so by C1 every worktree of the repo, the main checkout included, sees the same stash list. That fits B2 (entries made in the scratch worktree showed in the main checkout). [https://git-scm.com/docs/git-stash; https://git-scm.com/docs/git-worktree]
- C4. `git stash push` with a pathspec rolls the matching files back to HEAD "in the working tree and in the index ... leaving files that do not match the pathspec intact". Run in the main checkout, it would therefore revert another item's uncommitted edit to that file, which is the RI-009 / 032/06 failure. [https://git-scm.com/docs/git-stash]
- C5. Stash `drop`/`clear` entries "cannot be recovered through the normal safety mechanisms"; `clear` says entries "may be impossible to recover". An agent that drops or pops the wrong `stash@{n}` (another agent's or the person's) can lose it. [https://git-scm.com/docs/git-stash]
- C6. `git stash list` lists "the stash entries that you currently have", one per line (`stash@{0}: WIP on ...`). The page does not say what it prints, or which exit code it gives, when there are none: UNVERIFIED. [https://git-scm.com/docs/git-stash]
- C7. `git rev-parse --verify -q <ref>`: "Do not output an error message if the first argument is not a valid object name; instead exit with non-zero status silently." So `rev-parse --verify -q refs/stash` gives exit 0 and a sha when a stash exists, and non-zero when none exists. The page does not separate "no such ref" from "git failed" by exit code: UNVERIFIED that the two can be told apart this way. [https://git-scm.com/docs/git-rev-parse]
- C8. A related shared-ref leak: `git worktree add <path>` with no commit-ish and no `-b`/`-B`/`--detach` "is associated with a branch ... named after `$(basename <path>)`. If <branch> doesn't exist, a new branch based on `HEAD` is automatically created". By C1 that branch is a shared `refs/heads/` ref. `--detach` creates none ("detach `HEAD` in the new worktree"). A worktree dir named `wt` (091/05 L275) made this way would create a branch `wt` in the main repo. Whether 091 used that form is not recorded: UNVERIFIED. [https://git-scm.com/docs/git-worktree]
- C9. `git worktree remove` works only on clean worktrees unless `--force` is given; `prune` removes the info of worktrees whose dirs are missing. [https://git-scm.com/docs/git-worktree]

### D. Safe restore instead of stash
- D1. `git checkout [<tree-ish>] [--] <pathspec>` will "Replace the specified files and/or directories with the version from the given commit or tree and add them to the index"; "If not specified, the index will be used". Neither the path form nor anything else in this mode creates or moves a ref. [https://git-scm.com/docs/git-checkout]
- D2. So `git checkout HEAD -- <file>` in the scratch worktree restores a mutant from the commit. Plain `git checkout -- <file>` restores from the index, so a mutant that was staged would stay. N4's text (`git checkout -- <file>`) is safe only if mutants are never `git add`ed. [https://git-scm.com/docs/git-checkout]

### E. mkdtemp (already sourced in 091, re-checked 2026-11-24)
- E1. "There are no race conditions in the directory's creation. The directory is readable, writable, and searchable only by the creating user ID." "The user of mkdtemp() is responsible for deleting the temporary directory and its contents". [https://docs.python.org/3/library/tempfile.html]
- E2. "Changed in version 3.12: mkdtemp() now always returns an absolute path, even if dir is relative". The rule's `dir="<absolute scratchpad path>"` is still needed for Python 3.10/3.11 (RI-008). With `dir=None` the default is TMPDIR/TEMP/TMP, then `/tmp`, so a rule that left out `dir` would put dirs outside the scratchpad. [https://docs.python.org/3/library/tempfile.html]
- E3. Shell `mktemp -d` (what the orchestrator used, B1) was never sourced: 091 removed its own claim as UNSUPPORTED (work/091/03-handoff.md L55). The issue here is form and location (outside the scratchpad, not the rule's form), not proven non-uniqueness. [repo: work/091/03-handoff.md L55]
