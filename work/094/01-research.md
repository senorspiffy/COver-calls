## Findings (one claim per line, each with [source URL] or UNVERIFIED)
### What git does
1. `--single-branch` clones "only the history leading to the tip of a single branch". "Further fetches into the resulting repository will only update the remote-tracking branch for the branch this option was used for the initial cloning." [https://git-scm.com/docs/git-clone]
2. `--depth` "Implies `--single-branch` unless `--no-single-branch` is given". So a plain `git clone --depth 1` is a single-branch clone. That matches F2's d1s probe (plain `--depth 1` → `OPEN BRANCHES: none`, 092). [https://git-scm.com/docs/git-clone]
3. Without `--single-branch`, clone "creates remote-tracking branches for each branch in the cloned repository (visible using `git branch --remotes`)". [https://git-scm.com/docs/git-clone]
4. The usual fetch config is `fetch = +refs/heads/*:refs/remotes/origin/*`. Run with no refspec on the command line, `git fetch origin` uses the `remote.<repository>.fetch` values "as the refspecs—they specify which refs to fetch and which local refs to update". So `git fetch` never creates a remote-tracking ref for a branch the configured refspecs do not match. [https://git-scm.com/docs/git-fetch]
5. This explains F2's finding that `git fetch origin` in the single-branch clone still shows only origin/main: the refspec, not the clone depth, sets which branches appear. (Inference from 1 and 4. The observation itself is logs/audit/2026-11-22-090.md L110.) [https://git-scm.com/docs/git-fetch]
6. `--unshallow` converts "a shallow repository to a complete one, removing all the limitations imposed by shallow repositories". The text is about history only and says nothing about refspecs. That fits F2, where the clone still printed `OPEN BRANCHES: none` and 092 after `git fetch --unshallow`. So 090's recovery sentence ("run git fetch --unshallow") does not fix this case. [https://git-scm.com/docs/git-fetch]
7. Docs give the exact refspec text a single-branch clone writes as `+refs/heads/<branch>:refs/remotes/origin/<branch>`: UNVERIFIED in the git-clone page (it does not say). A1 observed `+refs/heads/main:refs/remotes/origin/main` with git 2.43.0 (logs/audit/2026-11-22-090.md L30). This is repo evidence, not a doc. [https://git-scm.com/docs/git-clone]
8. `git branch -r` lists "the remote-tracking branches", and `--no-merged` lists "branches whose tips are not reachable from <commit>". Both read local refs only. `open_branches()` (check_pipeline.py L1425) and `next_id()` (L1861) see only what the refspec has fetched. [https://git-scm.com/docs/git-branch]

### Refspec shapes the check must handle
9. A refspec is "an optional plus `+`, followed by the source <src>, followed by a colon `:`, followed by the destination <dst>". `refs/heads/*:refs/remotes/origin/*` without `+` also covers every branch. A test for the literal string `+refs/heads/*:...` would wrongly call that a single-branch clone. [https://git-scm.com/docs/git-fetch]
10. A pattern refspec "must have one and only one `*` in both the <src> and <dst>". [https://git-scm.com/docs/git-fetch]
11. Negative refspecs: a refspec prefixed by `^` "will instead specify refs to exclude. A ref will be considered to match if it matches at least one positive refspec, and does not match any negative refspec." So `+refs/heads/*:...` plus `^refs/heads/claude/*` hides branches even though the glob is present. "Is the glob there" is not enough on its own. [https://git-scm.com/docs/git-fetch]
12. A remote can have several fetch lines. Pro Git shows two `fetch =` lines for `master` and `experiment` ("You can also specify multiple refspecs for fetching in your configuration file"). The check must read every value. [https://git-scm.com/book/en/v2/Git-Internals-The-Refspec]
13. `git remote add` writes `fetch = +refs/heads/*:refs/remotes/origin/*`. That is the "full" shape. [https://git-scm.com/book/en/v2/Git-Internals-The-Refspec]
14. `git config get` "emits the last value" when a key appears more than once, and "If `--all` is specified, emits all values". It "Returns error code 1 if key is not present." [https://git-scm.com/docs/git-config]
15. Git 2.46 deprecated the mode options (`--get`, `--get-all`) in favour of subcommands (`git config get`). [https://www.kernel.org/pub/software/scm/git/docs/RelNotes/2.46.0.adoc] The repo's tests ran on git 2.43.0 (logs/audit/2026-11-22-090.md L28), which predates the subcommands. So `git config --get-all remote.origin.fetch` is the form that works on both. That the deprecated `--get-all` still works on current git: UNVERIFIED (the release note says "deprecated" and does not say "removed").
16. `remote.<name>.fetch` is "The default set of "refspec" for git-fetch". [https://code.googlesource.com/git/+/master/Documentation/config/remote.adoc]
17. `--mirror` "maps all refs (including remote-tracking branches, notes etc.)" and "implies `--bare`". A mirror's refspec is not `+refs/heads/*:refs/remotes/origin/*`, but it has no work tree, so the checker cannot run there. Out of scope. [https://git-scm.com/docs/git-clone]

### Recovery command for the printed line
18. `git remote set-branches <name> <branch>...` "Change[s] the list of branches tracked by the named remote". The named branches are "interpreted as if specified with the `-t` option on the `git remote add`". `-t <branch>` creates "a refspec to track only <branch>" "instead of the default glob refspec". [https://git-scm.com/docs/git-remote]
19. The docs do not show that `git remote set-branches origin '*'` writes exactly `+refs/heads/*:refs/remotes/origin/*`: UNVERIFIED. It is not run here (R1 has no shell). I1/I2 should pin it in the real-clone fixture. The other form, `git config remote.origin.fetch '+refs/heads/*:refs/remotes/origin/*'`, sets the documented default (finding 4) directly. Note that plain `git config <key> <value>` replaces a single value. Its behaviour when several values exist: UNVERIFIED (page not read for that case). The request's wording is "git config remote.origin.fetch ... && git fetch", while A1's F2 wording is "git remote set-branches origin '*' && git fetch origin". R2 has to pick one sentence, used in all three rule files.

### Remote comparison (optional second check)
20. `git ls-remote` "Displays references available in a remote repository". `--branches` (`--heads` is a deprecated synonym) limits it to refs/heads. Exit 0 "indicate[s] it successfully talked with the remote repository". So it needs the network or a reachable remote. Offline, or through the agent proxy, it can fail. Any failure has to be "not checked", never "none" (RI-014/081 rule). [https://git-scm.com/docs/git-ls-remote]
21. Stale refs: git keeps "local references to branches on remotes that have themselves deleted those branches" until `git fetch --prune` / `git remote prune`. Pruning acts "as a function of the refspec of the remote". So remote-tracking refs can over-report deleted branches (safe for `--next-id`: a higher ID). They can never show a head the refspec does not match. [https://git-scm.com/docs/git-fetch]
