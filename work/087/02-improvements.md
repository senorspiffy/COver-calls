## 3 ways FOR
1. **Fail closed on a value that starts with `&`, `!` or `*`, rather than allowing node properties.** Pick R1's lean (01 Open question 1) over the `(?:[&!]\S*[ \t]+)*` option. The reasons:
   - A real strict reader already draws the line here. StrictYAML rejects `a: !!str yes` with `TagTokenDisallowed: Found disallowed tag tokens` and `a: &node1 3.5` / `c: *node1` with `AnchorTokenDisallowed: Found confusing disallowed anchor token (surround with ' and ' to make text appear literally)` [https://hitchdev.com/strictyaml/using/alpha/restrictions/disallowed-yaml/] (WebFetch). Its list of removed features includes "Explicit tags", "Node anchors and refs" and "Flow style" [https://hitchdev.com/strictyaml/features-removed/] (WebFetch).
   - Wikipedia's Billion laughs page backs the general case: "either a parser with intentionally limited capabilities is preferred (like StrictYAML) ... or file formats that do not allow references" [https://en.wikipedia.org/wiki/Billion_laughs] (WebFetch; the "..." is the reader's).
   - Other languages agree that `!` means different things to different readers. Russian: "Теперь интерпретация зависит от используемого парсера. Элемент, начинающийся с `!` — это тэг." [https://habr.com/ru/post/710414] (WebFetch). Chinese: "!、%等也可能被YAML解析器赋予特殊含义" [https://aicoding.csdn.net/6a5dee57662f9a54cb9151dc.html] (WebFetch).
   - Failing closed needs none of the sub-grammar R1 could not verify (F18 aliases, F19 anchor/tag characters, verbatim `!<...>` tags). It costs 0 lines today (R1 F7). It also covers `*` aliases and a property alone on its line (`description: &d` / `  "x,`), which the allow option has to reason about separately.
   - Pin it with a value-start anchor and the RI-012 negative fixture (R1 fixture 13, `Audit & Efficiency`), plus a mutation that searches anywhere in the line (R1 M30). R1 fixtures 1-5 become error fixtures with a new property text. R1 fixture 12 becomes an error fixture.
2. **Apply the property and flow rules at every place a value can start, including the start of a line with no key, and pin that with fixtures.** YAML lets a value sit on the line after its key. Flow collections across lines are ordinary YAML, not an edge case. Japanese: "2つ目の例では、フローシーケンスを改行込みで記述して" [https://atmarkit.itmedia.co.jp/ait/articles/2312/26/news033.html] (WebFetch). Spanish: values "que empiezan por llave o corchete (que se parsearían como colecciones de flujo, no como cadenas)" [https://abacktools.com/es/blog/how-to-detect-and-fix-yaml-errors] (WebFetch).
   - R2 trace (not run): `description:` / `  [a,` / `tools: Read, Write` / `]` has `[` at the start of an indented line with no key. A rule written as "after `key: `" would miss it. R1 F22 says PyYAML does not enforce flow indentation, so this shape plausibly hides `tools:` the same way as A1's F3. That PyYAML outcome is UNVERIFIED (not run).
   - The fix is to reuse QUOTE_START_RE's prefix: optional `- ` run, then optional `key:` + `[ \t]+`, then the value start. The key group is optional (L32), so line start is covered for free, and R1's F7 grep already used that prefix. Add two fixtures, `description:` / `  [a,` ... and `description:` / `  &d "x,` .... The second is caught today by the quote rule, and with FOR 1 it would be caught earlier by the property rule. Pin whichever text R3 picks.
   - Add the F2 block-list fixture (`hooks:` / `  - "x,` ...) and A1-m3 as mutation M27, as R1 proposed.
3. **Decide p11 by failing closed (R1 option a). Treat `-` followed by a tab (F26) the same way.**
   - PyYAML 6.0.3 rejects `tools:\tRead, Write` (logs/audit/2026-11-20-080.md L69). PyYAML's own docs say "the best rule for tabs in YAML is to not use them at all" (R1 F28).
   - Other languages give the same advice. Dutch: "Tabs breken je YAML-script simpelweg." [https://www.datacamp.com/nl/blog/what-is-yaml] (WebFetch). Russian: "Сообщения об ошибках YAML существенно различаются между парсерами." [https://abacktools.com/ru/blog/how-to-detect-and-fix-yaml-errors] (WebFetch).
   - The runtime reader is unknown (R1 F29). An unparsed project agent is skipped (R1 F30). So "p11 means Read, Write" is the one answer the test cannot defend.
   - Rule: a tab anywhere in the prefix before the value start (after `-` or after `key:`) is an error. That covers p11 and `  -\t"x,` with one rule. It costs 0 lines today (R1 F7: 0 tabs).
   - This needs no `claude plugin validate` run (R1 option b) and matches 080 D8. M22 needs a new target, as R1 notes.

## 3 ways AGAINST
1. **Fail-closed rules will flag valid, mainstream YAML.** Anchors and flow lists are taught as normal features, not tricks. French: "YAML permet notamment de créer des ancres." / "Vous pouvez les réutiliser à différents endroits pour éviter les répétitions." [https://snyk.io/fr/blog/java-yaml-parser-with-snakeyaml/] (WebFetch). Chinese: "锚点 `&` 和 别名 `*`，可以用来引用" [https://cnblogs.com/Undefined443/p/18234278] (WebFetch).
   - The Claude Code docs' own `mcpServers` example has `args: ["-y", "@playwright/mcp@latest"]` (R1 fixture 14, 080 S7). A blanket value-start `[` rule turns that documented shape into a false error the day an agent adds it.
   - False alarms push people to weaken a check (080 AGAINST 1).
   - Cost control:
     - Error texts should say the test cannot read the value and how to rewrite it (quote it, or use a block list). They should not call the YAML invalid.
     - Add positive fixtures: `description: "&x"` (quoted, so the value start is `"`) and the a1-auditor mid-value `&`.
     - For flow, R3 picks one of two options. (a) Accept a flow collection that closes on its own line, using `_quote_end` for quoted entries and stopping at ` #` (R1 F23, M28, M29). This is more code. (b) Fail closed on every value-start `[`/`{` outside `tools:`/`disallowedTools:`, and list the `mcpServers` shape in the docstring's "Known fail-closed false errors" (L20-L21). That is 080's pattern.
2. **This is the third deny-list patch to the same parser, and the next prefix is already in view.**
   - 075 missed the quote shape, 080 missed properties and flow, and R1 found `? ` / `: ` (F25) and `-\t` (F26) before anyone probed them.
   - An English post-mortem of a regex frontmatter reader says the same: "YAML's flexibility is a footgun for code that parses it with regex instead of a full parser" [https://timetobuildbob.com/blog/yaml-has-two-faces-a-parsing-bug-hiding-in-plain-sight/] (WebFetch). In that case an inline `keywords: [...]` array made a regex return an empty list with no error. That is the RI-002 shape.
   - Asking a real parser does not settle it either. A yaml-test-suite issue says documents "parsed as expected by e.g. libfyaml, libyaml" fail in "pyyaml, SnakeYAML, YAML:PP, and Ruamel" [https://www.github.com/yaml/yaml-test-suite/issues/83] (WebFetch). So adding PyYAML (also ruled out by RI-008) would not give ground truth.
   - Alternative for R3, larger in scope: turn the check around into an allow-list. Every frontmatter line must match one of a few known shapes, else the error is "line the test cannot read": `key: <plain value starting with [A-Za-z0-9(]>`, `key:`, indented `- <plain>`, `key: "<closed>"`, and an indented nested `key: value`. Then `?`, `:`, `&`, `!`, `*`, `[`, `{`, `|`, `>` and tabs all fail without each being named.
   - R2 cannot say whether today's 7 files fit that list without the real tree test. R1 F7 says each file has only `name`/`description`/`tools` on L2-L4, which suggests they do (UNVERIFIED, not run). If R3 keeps the deny-list, R1's `?`/`:` fixture 15 and M31 should be adopted, not left optional.
3. **Precedence will silently change pinned results unless the plan names them.**
   - `_frontmatter_error` runs before `_field` (L158-L161). Four current fixtures put a flow list on `tools:`: g (L222), h (L223), j3 (L230) and v (L242). If the new flow rule is not exempted for `tools:`/`disallowedTools:`, g and h flip from positive to error, v changes from `empty tools:` to the new text, and j3 changes from `unclosed [ in tools: (item 075)`. That is four fixtures, not the one R1 named in Open question 2. The real-tree test is unaffected (0 value-start `[` lines, R1 F7).
   - The same applies to the property rule: `tools: &t Read` or `tools: !!str Read` gets the new property text instead of a `_field` error. Both are errors, but I1 must pin which text wins.
   - p11 flips from positive to error, so M22's target moves.
   - Mutation count grows. M25-M31 make 7 new mutations. Each one must be run, and its failing fixture named, by I2/I3.
   - The line number base is unchanged (`n = i + 2`, L134). Keep it, and re-check it against A1-m1.

## Holes to watch out for (summary)
1. **Value on the next line** (FOR 2): `description:` / `  [a,` and `description: &d` / `  "x,`. Every rule must use the full value-start prefix (optional `- ` run, optional `key:` + `[ \t]+`), not just "after `key: `". Pin each case with a fixture.
2. **Anchor the `&`/`!`/`*` check at the value start** (RI-012): a1-auditor's `Audit & Efficiency` and a quoted `"&x"` stay positive. Add mutation M30 (search anywhere in the line), which must fail the real-tree test.
3. **The tools flow fixtures** (AGAINST 3): g, h, j3 and v (L222, L223, L230, L242) must keep their results unless the plan changes them in the open. The easiest way is to exempt `tools:`/`disallowedTools:` from the new flow rule, since `_field` already handles them.
4. **Property on `tools:` itself**: `tools: &t Read` and `tools: !!str Read`. Decide which error text wins and pin it.
5. **The `mcpServers` `args: [...]` shape from the docs**: either accept a flow collection closed on its line (quote-aware and ` #`-aware, R1 F23, with M28 and M29), or list it as a known fail-closed false error in the docstring.
6. **Other prefixes** (`? `, `: `, `-\t`): adopt R1 fixture 15 and M31 if the deny-list stays, or move to the allow-list in AGAINST 2. Their PyYAML behaviour is UNVERIFIED (not run). A1 or I2 should probe them in a scratch dir.
7. **p11 flips to an error**: M22 needs a new target. Update the docstring (L15-L21) to list properties, open flow and tabs after an indicator, and keep the line that says the test says nothing about what Claude Code does.
8. **Don't resolve aliases or parse flow content.** Fail closed only. Alias expansion is a known resource risk (French row, Billion laughs), and 080 AGAINST 2 already advised against parsing multi-line flow.
9. **Source independence**: the Spanish and Russian abacktools rows are translations of one site, so count them as one source. The 080 rows (InfoWorld, abacktools es) overlap with this item's sources too.
