## 3 ways FOR
1. **Walk `git rev-list --first-parent <cutoff>..HEAD` and judge each commit C by `git diff --name-only C^1 C`, with 07 read at `C^1`.** This keeps R1's rule (code path changed → C must also change a step file of an item whose 07 at the parent has no `A1 result:`). It also closes R1's merge-commit gap. A merge into the checked branch is judged on everything it brings in against the first parent, conflict-resolution edits included. On main, each PR merge is one unit, so a PR whose code commit came before its 05 commit still passes as a whole. 3ba835e fails both ways: alone on a branch, and as de5406c on main (diff vs a30101c = config/tickers.json, tests/test_practice.py, work/048/05; 048/07 has PASS). Source for `--first-parent` ("follow only the first parent commit upon seeing a merge commit"): https://git-scm.com/docs/git-rev-list. `--no-merges` (R1's version) skips merges entirely, which is the gap R1 listed.
2. **Cutoff = a commit SHA, checked by ancestry, not a date.** Decision: a constant `UNTRACKED_FROM = "<40-char sha>"` set to the HEAD of daily-fixes/2026-11-11 just before I2's first code commit for 053. That commit's tree already holds 3ba835e, so 3ba835e is excluded, and 053 itself is judged by the new rule. The comment says "item 053; never move it forward" (same style as `LOG_TIME_EXCEPT`). `A..B` excludes everything reachable from A [https://git-scm.com/docs/git-rev-list]. So a branch cut before the cutoff and merged after it (e.g. PR #17 / 052) is still checked. A committer-date filter would skip such a branch's older-dated commits. Dates are per commit, not per merge, and R1 cites that `--since` can stop at the first older commit. A SHA can't be written into its own commit; the pre-build HEAD avoids that.
3. **Shallow clone and missing cutoff are told apart, never passed silently.** `git rev-parse --verify "<cutoff>^{commit}"` "will make sure `$VAR` names an existing object that is a commit-ish", and `--is-shallow-repository` prints "true" for a shallow repo [https://git-scm.com/docs/git-rev-parse]. Decision: cutoff missing and the repo shallow → `UNTRACKED CHANGE: not checked (cutoff <short> not in this shallow clone; run git fetch --unshallow)`, exit code unchanged (like `LOG TIME: not checked (no git)`). Cutoff missing and the repo not shallow → error, exit 1 (wrong SHA, or the PR was squash-merged or rebased). No git → `not checked (no git)`. This clone was fetched with `--depth 50` (R1, .git/logs/refs/remotes/origin/main), so the cutoff is present now but falls out after about 50 newer commits. A1 should unshallow once.

## 3 ways AGAINST
1. **Any open item covers any code in the same unit.** If C touches one step file of an open item, all of its code passes, even code unrelated to that item. Reasoning: the rule ties code to *an* open item, not to *its* item. The rule is also strict on a branch. There each direct commit is its own unit, so if I2 commits code first and 05 later, the code commit fails I3's run. Cost: I2 must commit code together with 04/05 changes. The run-item line should say so. Mitigation: list "cover" as a known gap in the docstring, like the blame gap at L56–57. A1 still reads diffs. Don't widen this item into file-to-item matching.
2. **The cutoff SHA is brittle.** A squash merge or rebase of this PR drops the branch-side SHA from main. Main would then fail every day (exit 1, by FOR 3) until someone edits the constant. Reasoning: only a merge commit keeps the branch commits as ancestors. PR #18 landed as de5406c ≠ 3ba835e, so it was probably a merge commit, but R2 could not run `git cat-file -p de5406c` to count the parents: UNVERIFIED (R3). The loud failure is deliberate (RI-002 spirit), but it is a cost if the merge style changes. I2 notes in 05 that the PR must be merged with "Create a merge commit", and I3 checks `git merge-base --is-ancestor <cutoff> HEAD`.
3. **Leaving PBR's `ex_div_date` null is the less protective choice for later expiries, and the derived date has a precedent.** If 2026-12-23 were entered, a held ITM call expiring after it would raise `EARLY_ASSIGN_CHECK_NA`, because the amount is unknown (ccbot/rules.py L214–219). With null, the report shows only "days to ex-dividend: n/a (not supplied)" and no event. The last cycle backs the derivation. The 6-K of 6 Aug 2026 gives B3 record 21 Aug, B3 ex 24 Aug and ADR record 25 Aug, but no ADR ex-date [https://www.sec.gov/Archives/edgar/data/0001119639/000129281426004123/pbr20260806_6k.htm]. stockanalysis lists ADR ex-div as 25 Aug (tickers.json source), so ADR ex = ADR record. Under T+1, FINRA 11140 sets ex = record [https://www.finra.org/rules-guidance/notices/24-04]. Still, the date is a derivation, and Brazilian press has given a different ADR ex-date before. In 2023 Suno wrote that shares go "ex-direitos" on B3 *and NYSE* from 22 Aug, with ADR record 23 Aug (Portuguese row). **Decision: keep null.** `tickers.ex_div_date` has no fallback row, and adding one is a rule change for the person (as 040 was). Write the ADR record date in the PBR `sources` text ("ADR record date 2026-12-23, ex-date not published"), so the person sees it. This has no effect on a Dec 18 2026 call (record date is 5 days after expiry, R1). It matters for any Jan 2027 PBR call; flag that in 05 and the A1 report. Offer "ADR ex = ADR record date (FINRA 11140), labelled" as a separate IDEA item.
