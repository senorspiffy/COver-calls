## 3 ways FOR
1. **Name Option B as the rule: `PYTHONDONTWRITEBYTECODE=1` + `PYTHONPYCACHEPREFIX=<empty dir>`. Keep "delete `__pycache__`" only as a fallback.**
   - Python's sys docs say that with the prefix set, Python reads and writes .pyc files only in that tree: "源代码树中所有的 `__pycache__` 目录都将被忽略" ("all `__pycache__` directories in the source tree will be ignored") [https://docs.python.org/zh-cn/3/library/sys.html].
   - Both variables are inherited by every child (R1 finding 9, and the repo check above). So one setting covers the parent pytest, the check_handoff -> check_pipeline import path (R1 finding 10), and pytest's rewriter (R1 finding 13).
   - Reasoning chain for a smaller recipe: with `dont_write_bytecode` true, `_cache_bytecode` is never called (R1 finding 7). So the prefix dir stays empty for the whole session, and one `mkdtemp()` per probe session is enough. No per-mutant recursive delete is needed, and nothing depends on the timing of the restore. This is an inference from R1's code reading, not a documented guarantee. I2 should assert that the dir is still empty after a run.
2. **Upstream will not fix this for us, so the repo-side guard is justified rather than over-engineering.**
   - CPython bpo-31772 says: "The current import machinery will use stale cached bytecode if the source is modified more than once per second" [https://bugs.python.org/issue31772].
   - The issue was closed "wont fix" in favour of PEP 552 hash pycs and later reopened. A proposed fix (recompile when source mtime == now) "wasn't merged". The reporter also noted that "hash-based checking will not become the default" (same page, as summarised by fetch).
   - A 2024 discuss.python.org thread still describes "the python use the old bytecode cache because of the timestamp issue". There, "there is no guarantee that better than 1 second resolution of the time stamp is available across OSes" [https://discuss.python.org/t/change-pyc-file-format-to-record-more-accurate-timestamp-and-other-information/57815].
   - So the hazard is current, documented behaviour on the project's Python 3.10-3.13 range. Whether any 3.14+ release changed it is UNVERIFIED.
3. **Make the guard checkable, not just written (RI-010 lesson). Fold it into probe_guardrails' `_child_env` and add a printed self-check, rather than writing a new script.**
   - probe_guardrails already owns the child env (L162-165) and is the one place 074 tested. Adding `PYTHONPYCACHEPREFIX` there and exposing a tiny `--env-check` (a child `python -c "import sys; print(sys.dont_write_bytecode, sys.pycache_prefix)"`, same pattern as `module_file` L181-185) would give a line I2/I3/A1 can paste into 05/06. R3/A1 could then grep for that line instead of trusting prose.
   - For the "Done looks like" probe, add the `-B`-only negative case R1 proposed (old .pyc present, `-B`, stale read expected). That pins R1 finding 7, so nobody can later "simplify" the guard to `-B`. The Japanese docs wording supports why the case is needed: `-B` means Python "`.pyc` ファイルの作成を試みません" ("will not try to create .pyc files"). It talks about creating only and says nothing about reading [https://docs.python.org/ja/3/using/cmdline.html].

## 3 ways AGAINST
1. **A rule that lives only in agent text has already been skipped 3 times, and changing `.claude/` needs the person's OK.**
   - 080/07, 085/07 and 101/07 each asked for `-B` / env var / clearing (R1 brief L8), yet 101 and 103 still hit stale bytecode. That is the RI-010 pattern (duties only in agent text get skipped).
   - The four agent files are under `.claude/` (R1 open question 5), so the text change can wait in PR review. Until then, a probe that does not go through a checked helper is unprotected.
   - Cost if FOR 3 is taken instead: one more flag and tests in probe_guardrails.py, which is a guardrail script with its own mutation suite (074). That is more surface to keep green.
2. **Neither option covers every way a probe can read old code. Agents may treat "env var set" as proof.**
   - Sourceless .pyc: Python "non controlla la cache se non esiste il modulo sorgente" ("does not check the cache if the source module does not exist"). A legacy `x.pyc` placed in the source directory is imported when `x.py` is absent [https://docs.python.org/it/3/tutorial/modules.html]. The Russian Q&A makes the same point: "Если нет исходного файла, кэш в каталоге __pycache__ будет проигнорирован" ("if there is no source file, the cache in `__pycache__` is ignored") [https://qna.habr.com/q/531673].
     - So a "move the file out" mutant (like 103 m3) is safe from `__pycache__` but not from a stray legacy .pyc beside the source, and PYTHONPYCACHEPREFIX does not change that lookup (reasoning: the prefix only redirects the `__pycache__` cache path).
     - The risk is low here: no .pyc is tracked (030), and worktrees are fresh. The pytest-remove-stale-bytecode plugin exists for exactly this case: "This plugin removes all stale bytecode files before running tests" [https://pypi.org/project/pytest-remove-stale-bytecode/5.0/].
   - In-process caching: a probe that mutates a file and re-imports it in the same interpreter (same pytest session, `importlib.reload` omitted) gets the old module object from `sys.modules`. Neither bytecode setting helps there. Source: the import system checks `sys.modules` first [https://docs.python.org/3/reference/import.html]. That page was cited by R1 but not re-fetched by R2, so the exact quote is UNVERIFIED.
   - UNCHECKED_HASH pycs are never validated: "Python 将在运行时假定 `.pyc` 文件是最新的而完全不会将 `.pyc` 与源文件进行验证" ("Python will assume at runtime that the .pyc is up to date and will not validate it against the source at all") [https://docs.python.org/zh-cn/3/library/py_compile.html]. Option A's delete and Option B's prefix both remove this risk. `-B` alone does not.
3. **Scope and payoff are small and indirect. The bigger risk is duplicating logic or over-claiming.**
   - Only 3 hand-run sed probes were hit, in 6 days (R1 numbers). probe_guardrails, the automated path, is already safe by R1 findings 7 and 9 (fresh worktree + env var).
   - A separate `scripts/run_mutant.py` (R1 open question 2) would be a second copy of `_child_env`, and the two could drift.
   - Every guarded run compiles all imported modules from source and re-runs pytest's assertion rewrite, because nothing is ever cached. The extra seconds per mutant are UNVERIFIED: 103/06 shows 0.19 s for a `-k` run but does not separate out compile time.
   - Listing `-p no:cacheprovider` next to the bytecode settings invites the wrong belief that it is a bytecode guard (R1 finding 16). The agent text should label it as ".pytest_cache hygiene", or drop it from the bytecode rule.

## Holes to watch out for (summary)
- `-B` and PYTHONDONTWRITEBYTECODE stop writing only. Every language's docs word it that way (es, ja). They never make an existing stale .pyc safe.
- `-B` does not reach `[sys.executable, ...]` children. The env var does, because every current child inherits `os.environ` (repo check).
- If PYTHONPYCACHEPREFIX is set, deleting in-tree `__pycache__` does nothing (zh-cn sys doc). It is unset in this container today (orchestrator fact), but the guard should print or assert `sys.pycache_prefix` rather than assume it.
- If the prefix dir is reused while writing is on, it becomes the new stale cache, a mirrored tree (ja Qiita). Keep the env var on, or use a fresh dir per run.
- Sourceless legacy `x.pyc` beside a removed `x.py` still imports (it, ru). This matters for "move file out" mutants. It is low risk while no .pyc is tracked (030).
- A module already in `sys.modules` is not re-read in the same process. Bytecode settings don't help (quote UNVERIFIED, see AGAINST 2).
- UNCHECKED_HASH pycs are never validated (zh-cn py_compile). The prefix or a delete covers this; `-B` does not.
- `-p no:cacheprovider` is .pytest_cache hygiene, not a bytecode guard (R1 finding 16).
- `os.utime` behaviour in the proposed "Done looks like" probe is still UNVERIFIED (R1). I2 should show the unguarded case reads stale before trusting the guarded case.
- Upstream: bpo-31772 is still unmerged. Whether 3.14+ changed the timestamp check is UNVERIFIED.
