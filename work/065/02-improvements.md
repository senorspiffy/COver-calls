## 3 ways FOR
1. **Build the one helper from the bracketing dates, and give each edge its own mutation.** `td.earnings` is already sorted and de-duplicated (`sorted(set(...))`, realtest L184), so `bisect` on it is safe. Let a = the last listed date on or before d, and b = the first listed date on or after d. Then d is known iff a and b both exist and `(b - a).days <= EARNINGS_GAP_WARN`. If d is a listed date, a == b and the gap is 0. Before the first date there is no a (063's edge). After the last date there is no b (the trailing edge). This meets request § Guardrail 3. I3 should then run three mutations, each of which must make tests fail: (i) drop the "a exists" check (063's tests: `test_leading_edge_100_days_blocks`, `test_leading_edge_151_days_blocks`, `test_drop_input[earnings_before_first]`, REAL_BAC pins); (ii) drop the "b exists" check (`test_stock_without_earnings_sells_nothing`, tests L227-229; R1 finding 4 says this is UNVERIFIED until run); (iii) drop the gap check (the new 180-day fixture). Reasoning chain: with one helper, a future edit can't fix one edge and miss the others. With three mutations, no single clause in it is left untested. Also compute the `load_ticker` warning count from the same constant and the same comparison (`> EARNINGS_GAP_WARN` warns iff the helper blocks). Then VALE's exactly-120-d interval (01 finding 9) is neither warned nor blocked, the same way in both places.
2. **Design the fixture so only the interior check can block the sale, and pin the boundary.** R1 open question 2 shows that a call whose life reaches the gap's start date a is already caught by `_earnings_between` (EARNINGS_BLACKOUT). A fixture whose call life touches a listed date would therefore pass with the interior check removed, and mutation (iii) would show nothing. The 180-d fixture needs: the sale day strictly inside the gap, and no listed date in [d, expiry]. The test should assert `rej_EARNINGS_UNKNOWN >= 1`, no trade, and no EARNINGS_BLACKOUT. Add a boundary pair too: the same layout with a gap of exactly 120 d sells, and 121 d is blocked. That pins `<=` against the warning's `>`. The 3 control fixtures (tests L219, L274, L288) need the 118-d replacement pair [2023-10-25, 2024-02-20] (01 § Numbers: 6 + 30 + 31 + 31 + 20 = 118, and 02-20 is after the 02-16 expiry). I1 should list each one as "fixture gap shortened so the control stays a control; assertion unchanged" (the pattern from 063).
3. **Count it separately, word it plainly, and keep the cost small.** EARNINGS_UNKNOWN now has three causes (no file, leading edge, interior gap). If only that code is counted, 05 cannot show the MO/MDLZ effect apart from 063's edge. Add a per-stock count of attempt days blocked inside an interior gap (for example `earnings_gap_days`) next to `earnings_gaps_gt120` (realtest L608/L762 per 01 finding 1). Add a `REALTEST_MISSING` row such as `"earnings_interior_gap": "EARNINGS_UNKNOWN inside a gap > 120 d between listed dates; warning"`, which the enumeration test `test_realtest_missing_lists_every_input` (realtest L66-67) will require anyway. Extend the warning text the way 063 did: "...; no call sold inside them (EARNINGS_UNKNOWN)" when `rule.skip_earnings`, otherwise "earnings not checked by this rule" (realtest L415-416). Cost: at most 6 sales are blocked directly (MO 2, MDLZ 4), and CMCSA/T/VZ lose none (01 findings 18-20). The fix removes the 2 sales that held a call through a real report missing from the file (MO 2022-01-19 and MDLZ 2022-01-24, against the 2022-01-27 releases in 01 findings 13-14). On a 1-lot account that one call is the whole position (01 § Fit).
