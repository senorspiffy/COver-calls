# 01 Research brief - 079
## Question
`scripts/check_pipeline.py::_walk` (L594-613 on this branch) checks shallowness only when the cutoff is unreachable. When the cutoff is reachable but the walk contains a shallow-boundary commit, `diff-tree c^1 c` fails and `untracked_changes` prints it as an error entry (exit 1). What does git document about shallow boundaries, how can the checker tell a shallow boundary apart from a real failure, and which of the three walk users (UNTRACKED CHANGE 053, RESEARCH CODE 062, REAL-DATA FIELD 070) can give a wrong answer because of one?

Read first: logs/recurring-issues.md RI-014 (this item, OPEN, 1 occurrence) and RI-002/RI-007; logs/audit/2026-11-19.md L32/L44; work/053/01-03 (the existing shallow handling for a missing cutoff, `test_cutoff_missing_in_shallow_clone_not_checked`); logs/audit/2026-11-18-069.md L147/L156 (INBOX shallow guard, mutation g4). Nothing earlier covers a boundary *inside* the walk.

## Findings (one claim per line, each with [source URL] or UNVERIFIED)
Git facts
- The shallow file "lists commit object names and tells Git to pretend as if they are root commits (e.g. "git log" traversal stops after showing them ...)"; each line holds exactly one object name [https://git-scm.com/docs/shallow].
- "Shallow commits do have parents, but not in the shallow repo, and therefore grafts are introduced pretending that these commits have no parents." [https://git-scm.com/docs/shallow]
- `git rev-parse --is-shallow-repository`: "When the repository is shallow print "true", otherwise "false"." [https://git-scm.com/docs/git-rev-parse]
- `<rev>^<n>` means the nth parent; the docs say nothing about a missing parent. That a shallow boundary's `c^1` fails to resolve (so `diff-tree c^1 c` exits non-zero) is documented only indirectly, through "pretend ... root commits" [https://git-scm.com/docs/git-rev-parse], [https://git-scm.com/docs/shallow]. The request's repro (a15129c in .git/shallow → `(git diff-tree failed)`) shows it in practice.
- `rev-parse --shallow-file`, named in the request's guardrail, is not on the git-rev-parse page (only `--is-shallow-repository` is) [https://git-scm.com/docs/git-rev-parse]. UNVERIFIED as a usable option. Do not rely on it.
- The shallow file is `$GIT_DIR/shallow`, but "This file is ignored if $GIT_COMMON_DIR is set and "$GIT_COMMON_DIR/shallow" will be used instead" [https://git-scm.com/docs/gitrepository-layout]. In a linked worktree, `$GIT_DIR` is the private `.git/worktrees/<name>` dir and `$GIT_COMMON_DIR` is the main `.git` [https://git-scm.com/docs/git-worktree]. The audit that found this ran in a worktree (request Evidence 1), so reading a literal `.git/shallow` would miss it there (in a worktree `.git` is a file [https://git-scm.com/docs/git-worktree]).
- `git rev-parse --git-common-dir`: "Show `$GIT_COMMON_DIR` if defined, else `$GIT_DIR`." `--git-dir` output "when relative, is relative to the current working directory" [https://git-scm.com/docs/git-rev-parse]. So `<git-common-dir>/shallow` is the documented location in both a plain clone and a worktree.
- git-worktree advises: "do not make any assumption about whether a path belongs to `$GIT_DIR` or `$GIT_COMMON_DIR` ... Use `git rev-parse --git-path` to get the final path." [https://git-scm.com/docs/git-worktree]. Whether `--git-path shallow` maps to the common dir is not stated on that page: UNVERIFIED. I2 should pin one of the two forms in a worktree fixture.
- `git fetch --unshallow`: "If the source repository is complete, convert a shallow repository to a complete one ... If the source repository is shallow, fetch as much as possible so that the current repository has the same history as the source repository." [https://git-scm.com/docs/git-fetch]. So the hint can still leave a clone shallow when the source is shallow; the check must re-test, not assume.
- `git clone --depth` "Implies `--single-branch` unless `--no-single-branch` is given" [https://git-scm.com/docs/git-clone]. actions/checkout defaults to `fetch-depth: 1` ("0 indicates all history") [https://github.com/actions/checkout]. A CI run of the checker would therefore be shallow by default (the repo has no CI today, RI-010 note).
- `log.showRoot` is "True by default": a root commit is shown "as a big creation event ... equivalent to a diff against an empty tree" [https://code.googlesource.com/git/+/7381be0d632ac41b4ffb083a8d0a8eb2ff32d834/Documentation/config/log.adoc]. `diff-tree --root` does the same, and without it a single commit "is compared with its parents" [https://git-scm.com/docs/git-diff-tree].

Code findings (read on this branch; line numbers in scripts/check_pipeline.py)
- F1 (the reported bug): L599-605 test `--is-shallow-repository` only when the cutoff is unknown or not an ancestor. L610-612 run `diff-tree -r --name-only --no-renames c^1 c` per walked commit and store `None` on failure. `untracked_changes` L627-629 turns `None` into the entry `<sha7> (git diff-tree failed)`, which sets failed=True.
- F2 (a silent pass, the "or as a pass" in the request): `research_code` L659 uses `files or []`, so the same `None` becomes "this commit changes nothing". A RESEARCH ONLY item's code commit at a boundary would give `RESEARCH CODE: none` (RI-002 pattern).
- F3 (silently missing commits): a boundary has no parents in the shallow view [https://git-scm.com/docs/shallow], so `rev-list --first-parent cutoff..HEAD` (L606) stops there. The first-parent commits between the cutoff and the boundary are never walked. Those hidden commits can't be flagged, so this direction is a silent pass even if the boundary's own diff is skipped. Not seen in the evidence. It follows from the doc: UNVERIFIED by a probe.
- F4 (070 path, not first-parent): `_item_triggers` L707 runs `git log --no-merges --no-renames --name-only cutoff..HEAD` over all parents. A boundary on a second-parent side is invisible to a first-parent check, and with log.showRoot true git log shows it as a creation event listing every file in its tree [https://code.googlesource.com/git/+/7381be0d632ac41b4ffb083a8d0a8eb2ff32d834/Documentation/config/log.adoc]. That could produce a false REAL-DATA FIELD entry (trigger files the commit didn't change), or a missed one (commits behind the boundary). UNVERIFIED by a probe.
- F5: main() L857-860 computes `walked` once and passes it to all three. `research_code` L650 and `real_data_field` L733 already map a `_walk` error to "not checked (see UNTRACKED CHANGE)". So one `(None, (text, False))` return from `_walk` covers 053, 062 and 070 at once, and the 070 range in F4 too if the check uses the full range.
- F6 (telling shallow apart from a real failure): "parent is missing" alone is not shallow-specific. A real root commit in the range (e.g. a merged unrelated history) also has no `c^1` in a full clone, and that should stay a loud error. Use membership in the shallow file, not a missing parent. A diff-tree failure on a commit *not* in the shallow file stays an error entry (failed=True) as today.
- F7 (proof the check is complete): grafts only remove parent edges [https://git-scm.com/docs/shallow]. Take the boundary set S (shallow file) and R = `git rev-list cutoff..HEAD` (all parents, shallow view). If S ∩ R is empty, every boundary that HEAD can reach is an ancestor of the cutoff, so every parent a boundary hides is also an ancestor of the cutoff, and the full clone's `cutoff..HEAD` is exactly R. Then the 053/062/070 answers match the full clone. If S ∩ R is not empty, the answer can differ → "not checked". This is my own reasoning from the doc: UNVERIFIED by a probe. It is the design argument for "same answer or not checked".
- F8 (existing tests): `tests/test_pipeline_check.py` L729-741 already builds a shallow fixture with `git clone -q --depth 1 file://<repo>` and asserts `--is-shallow-repository` == "true". So depth over `file://` works with this git. The git-clone page doesn't promise it [https://git-scm.com/docs/git-clone]. The new fixture can't get a boundary inside a reachable-cutoff walk from `--depth` alone (depth counts every parent path, so the cutoff is cut too). Writing the boundary sha into `<git-common-dir>/shallow` is the request's own repro and is the documented file format [https://git-scm.com/docs/shallow]. Does writing that file by hand flip `--is-shallow-repository` to true? UNVERIFIED. The fixture should assert it, as L735-737 does.

## Numbers used (show the math)
- Request Evidence: 1 false entry (a15129c), exit 1 before unshallow, `UNTRACKED CHANGE: none` after. These are A1's numbers, not re-run here (no shell).
- Fixture shape (proposal, no counts asserted beyond these): commits C (cutoff) → P → B on main; side S with parent C; M = merge(first parent B, second parent S). B goes in the shallow file. Shallow-view first-parent walk C..M = {M, B} (P hidden behind B, F3). C is still an ancestor of M through S, so the L600 guard does not fire. R = rev-list C..M = {M, B, S}, S ∩ R = {B} → not checked. Expected line: `UNTRACKED CHANGE: not checked (shallow boundary <B7>; run git fetch --unshallow)`, exit 0; RESEARCH CODE and REAL-DATA FIELD `not checked (see UNTRACKED CHANGE)`.
- Mutation: remove the S ∩ R check → B's diff-tree fails → `<B7> (git diff-tree failed)`, exit 1 → the fixture fails.
