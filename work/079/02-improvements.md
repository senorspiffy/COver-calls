## 3 ways FOR
1. **One rule in `_walk`: boundary set S intersected with the full-parent range R = `git rev-list <cutoff>..HEAD`.** Put it after the ancestor check (L600) and before the diff-tree loop (L610). If `--is-shallow-repository` is true and S ∩ R is not empty, return `(None, (f"not checked (shallow boundary {b[:7]}; run git fetch --unshallow)" + note, False))`, with b the first boundary in R's order. Reasoning (R1 F5/F7): main() L857-860 hands one `walked` to all three users. research_code L650 and real_data_field L733 already map a `_walk` error to `not checked (see UNTRACKED CHANGE)`. So this one return covers 053, 062 and 070, and it also covers 070's all-parent `git log` range (F4), which a first-parent-only test would miss. If S ∩ R is empty, grafts only cut parent edges [https://git-scm.com/docs/shallow], so every hidden parent is already behind the cutoff and the answer equals the full clone's. That gives "same answer or not checked", as the request asks. Take the whole-range option (R1 open question 1). It is one call, `rev-list` with no `--first-parent`. Its only cost is a "not checked" when a boundary sits only on a side branch, and that is the safe direction.
2. **Read S from `<git rev-parse --git-common-dir>/shallow`, never a literal `.git/shallow`, and never `rev-parse --shallow-file`.** gitrepository-layout says about `shallow`: "This file is ignored if $GIT_COMMON_DIR is set and "$GIT_COMMON_DIR/shallow" will be used instead" [https://git-scm.com/docs/gitrepository-layout]. In a linked worktree `.git` is a file [https://git-scm.com/docs/git-worktree], so a literal path breaks in exactly the setup where the bug was found. This settles R1's UNVERIFIED `--git-path` question. git's own source lists `"shallow"` in `common_list` with the is-common flag set (`{ 0, 0, 1, "shallow" },`) [https://raw.githubusercontent.com/git/git/master/path.c]. So `--git-path shallow` also resolves to the common dir, and either form works. Pick `--git-common-dir` (documented on a man page) and resolve it relative to the cwd, because "when relative, is relative to the current working directory" [https://git-scm.com/docs/git-rev-parse]. `--shallow-file` is not a documented rev-parse option (R1 L13). Drop it from the guardrail text. A missing or unreadable file while `--is-shallow-repository` says true becomes `not checked (shallow clone; ...)`, never a pass.
3. **Keep real failures loud and close the silent-pass path too.** (a) Use membership in S, not "parent missing", to call a commit a boundary. A genuine root commit in the range (unrelated history merged in) has no `c^1` in a full clone either, and must stay `<sha7> (git diff-tree failed)`, exit 1 (R1 F6). (b) Defence in depth for F2: in `research_code`, a `None` diff must not become `[]`. Make it either the not-checked text or skip-with-053-entry, so a future change to `_walk` can't bring back a silent `RESEARCH CODE: none`. (c) Fixtures: boundary on the first-parent walk with the cutoff reachable through a side parent (R1's C→P→B, S, M shape) → all three `not checked`, exit 0. A boundary only on a side branch → also not checked (pins the whole-range choice). A linked worktree of the grafted repo (`git worktree add` in tmp_path) → same text (pins FOR 2). A full clone of the same history → unchanged answers. Mutations: drop the S ∩ R test (→ exit 1, `(git diff-tree failed)`); read `.git/shallow` literally (→ the worktree fixture fails). (d) Process line in daily-audit.md / run-item.md: "if `git rev-parse --is-shallow-repository` prints true, run `git fetch --unshallow`, then re-test it before `check_pipeline.py`". The re-test is needed because --unshallow from a shallow source "fetch[es] as much as possible", which can leave the clone shallow [https://git-scm.com/docs/git-fetch].

## 3 ways AGAINST
1. **The simpler blanket rule (INBOX's) may be enough.** `_inbox_gate` L790-794 says `not checked` whenever the repo is shallow. Copying it into `_walk` needs no file read, no worktree path question and no set logic, and the request's "same answer or not checked" still holds. Reasoning for why it might suffice: the daily audit unshallows anyway (the process line), and the repo at rest is not shallow (no `.git/shallow` here). Cost of the blanket rule: a deep-but-shallow clone (053 noted a `--depth 50` fetch) would lose a check that works today, and so would a CI checkout of any depth ([https://github.com/actions/checkout] defaults to `fetch-depth: 1`, but there the cutoff is missing anyway, so 053's message already fires). Verdict: the precise S ∩ R check is worth its ~10 lines because it keeps the guard live on depth-N clones. I1 may still pick the blanket rule. If so, write it down as a decision.
2. **"not checked" with exit 0 weakens the RI-007 guard on shallow clones.** Whatever sits behind a boundary is not inspected, and the run is green. Someone who never unshallows gets no failure at all. Reasoning: the exit code says nothing, only the text does. Mitigation (keep it, don't change exit 0, which follows the 053/069 precedent): the text names the boundary sha and the unshallow command; A1's report must quote the line as "not checked", never "none"; the process line makes unshallow plus re-run the rule before the daily audit counts. If I1 wants it stricter, an option is exit 1 under a `--strict` flag. That is out of scope here: UNVERIFIED need.
3. **The fixture relies on hand-writing the shallow file, and that behaviour is only partly documented.** The file format is documented (one object name per line [https://git-scm.com/docs/shallow]), and the request's repro shows git honours a hand-written file for diff-tree. Whether `--is-shallow-repository` then prints true is UNVERIFIED (R1 F8). If it doesn't, the `_walk` guard (which gates on it) would skip the check and the fixture would wrongly fail or pass. The fixture must assert `--is-shallow-repository` == "true" after the write, as L735-737 does, and write the full 40-char sha plus a newline into `--git-common-dir`/shallow. Also, 076 and 077 change check_pipeline.py first (brief L3), so every line number here (L594-613, L659, L707, L857-860) must be re-read on top of 077.

## Holes to watch out for (summary)
- Don't use a literal `.git/shallow` (it breaks in worktrees) or `rev-parse --shallow-file` (undocumented).
- Don't call "parent missing" a boundary. Real root commits must stay loud.
- F3: commits hidden behind a boundary are never walked. Only the S ∩ R test catches that case, and skipping just the boundary's own diff is not enough.
- F4: 070's `git log` uses all parents, and log.showRoot can list a boundary's whole tree as changes. The whole-range check covers it. A first-parent-only check would not.
- The fixture must assert `--is-shallow-repository` is true after hand-writing the file.
- `git fetch --unshallow` can leave a clone shallow. Re-test it, don't assume.
