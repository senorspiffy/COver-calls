## 3 ways FOR
1. **Allow-list column-0 shapes (blank, `#...`, `key:` + space/tab/end of line) and run the check last within each line. This closes the RI-002 root cause at column 0 without naming each bad shape.**
   - Strict subsets are now mainstream practice, and Kubernetes made one for this reason. Japanese: KYAML is "標準YAMLの厳格なサブセット(もしくは「方言」)" and was made because "YAMLが多くの選択肢を与えてくれる" [https://kubernetes.io/ja/blog/2026/08/11/how-to-pretty-print-kubernetes-yaml-as-kyaml/] (WebFetch). A test that reads only a subset must refuse whatever falls outside it, which is 075's AGAINST 1 restated.
   - The key test must accept end of line after the colon (R1 F15: 20 empty-valued-key fixtures). Chinese teaching material states the rule in exactly that form: "冒号后面必须有一个空格或换行" [https://support.huaweicloud.com/intl/zh-cn/devg-cci/cci_05_1001.html] (WebFetch). Turkish material gives the same rule: "İki nokta'dan \":\" sonra bir boşluk varsa bu bir dictionaryi temsil eder." [https://dev.to/enesgerem/yaml-1men] (WebFetch). A tab after the colon is already caught earlier by TAB_BEFORE (L182-L183), so allowing `[ \t]` in the key test changes nothing.
   - Order: put the new check after the existing per-line checks (R1 OQ3). Then q16, q17, p15, q27, q28 and s_no_space keep their texts (R1 F13), and M46 pins the order. This costs 0 real lines (R1 F9: 21 of 21 are `key: `).
   - The error text should say the test cannot read the line (A1's draft `no key on frontmatter line <n>`). It should not claim a PyYAML line number. See AGAINST 3.
2. **Build the key test from the YAML indicator list, not by copying VALUE_START_RE's key group, and refuse a column-0 `- ` even when a colon follows.**
   - R2 trace (not run): VALUE_START_RE's key group starts with `[^\s"'#&!*\[{?:]` (L45). That allows `-`, `%`, `@`, the grave accent, `|`, `>`, `,`, `]` and `}` as a key's first character. Reused as-is, column-0 `- a: b` matches as a "key" (`-`, then ` a`, then `:` + space). So `name: x` / `- a: b` / TOOLS passes the new rule, although it is the same column-0-item-after-a-scalar shape that A1 measured as a ParserError for `- a` (logs/audit/2026-11-22-087.md L83-L84). This is a hole in R1 mutation M44 as well: a rule that only checks "no colon" would let it through.
   - German and Spanish error guides describe this exact parser message: "er stieß auf ein - Listenelement, wo er einen Schlüssel erwartete" [https://abacktools.com/de/blog/how-to-detect-and-fix-yaml-errors] and "se topó con un elemento de lista - donde esperaba una clave" [https://abacktools.com/es/blog/how-to-detect-and-fix-yaml-errors] (both WebFetch, same site, count as one source).
   - Proposal: the key's first character must not be any indicator in R1 F24, except `-` when the next character is not a space, tab or end of line. That keeps `---x: z` (F8) working and keeps `.` for `...x: y`, since `.` is not an indicator. `z_space_before_colon` (`tools :`) still counts as a key (R1 F14).
   - Add fixtures `name: x` / `- a: b` / TOOLS → no-key error, and `name: x` / `%x: y` / TOOLS → no-key error. Add a mutation that reuses the L45 key group unchanged and fails both. The PyYAML results for `- a: b` and `%x: y` are UNVERIFIED (not run). I2 or A1 should probe them in a scratch dir before 04 calls them invalid.

## 3 ways AGAINST
1. **The allow-list makes new false errors on valid YAML, and some of them come from how the test splits lines, not from YAML.**
   - Keys that contain a colon not followed by a space (`a:b: c`) are valid plain keys, but `[^:]*:` stops at the first colon and `b` is not space or end of line. That gives a no-key error. R2 trace (not run). The YAML side (a colon inside a plain scalar is allowed when not followed by a space) is supported by the Turkish source's rule that a colon in a value must be written "boşluk olmadan, escape karakteriyle ya da tırnak içinde" [https://dev.to/enesgerem/yaml-1men] (WebFetch).
   - `str.splitlines()` (L203) splits on more than CR/LF. The Python docs table includes "\x1e" | "Record Separator", and the bug report is titled "Python treats ASCII record separator ('\x1e') as a newline" [https://mail.python.org/pipermail/python-bugs-list/2018-August/375874.html] (WebFetch). So a description with such a character would produce a column-0 fragment that is not a key, and the new rule would call it a no-key error. That YAML 1.2 treats only CR and LF as line breaks is UNVERIFIED (R1 could not read that spec chapter, R1 F22). 0 real lines are affected (R1 F9).
   - Cost control: list both cases in the docstring's "Known fail-closed false errors". Keep "This says nothing about what Claude Code does". False alarms push people to weaken a check (080/087 AGAINST 1).
2. **This only fixes column 0. The same root cause stays on indented lines and inside values, so a fifth item is likely.**
   - `name: x: y` / TOOLS. Educative's standard "mapping values are not allowed here" example is `key1: value1:`, caused by "an unnecessary colon after `value1`" [https://www.educative.io/answers/unable-to-parse-yaml-mapping-values-are-not-allowed-here] (WebFetch). R2 trace (not run): VALUE_START_RE takes `name: ` and c = `x`, and the new rule sees a valid `key:` at column 0, so the test still returns {Read, Write}. 0 real lines (Grep above).
   - `name: x` / `  foo: bar` / TOOLS is an indented `key: value` under a scalar value. R2 trace (not run): no current check fires. The PyYAML result is UNVERIFIED (not run).
   - Implicit keys have limits that the test does not model. PyYAML's own test data says "A simple key is restricted to only one line. - A simple key must not be longer than 1024 characters." [https://fuchsia.googlesource.com/third_party/pyyaml/+/refs/tags/5.2/tests/data/spec-10-08.error] (WebFetch). A column-0 key longer than 1024 characters would pass the new rule but fail PyYAML. That is a false pass, with 0 real lines.
   - Per 053, these are a new item and not scope growth for 096. R3 should name them in 03 so I1 does not silently widen 096. They also strengthen 087 AGAINST 2's case for a whole-line allow-list as a separate IDEA/BUG.
3. **More cases, mutations and order rules to keep in sync, and the line number may not match what a real parser reports.**
   - The projection grows from 92 to 98 or 99 tests (R1). FOR 2 and FOR 3 add about 3 to 4 more fixtures and 2 more mutations on top of M42-M46. Each one must be run and its failing fixture named by I2/I3 (087 AGAINST 3).
   - Option (b) in FOR 3 adds state to a function that was stateless per line. A wrong reset (a blank or comment line between `tools:` and `- Read`) is a new bug surface. `_field` already treats that gap as an error (L76-L77, L85-L86), so the new check must not contradict it. Pin it with one fixture.
   - Parsers report errors away from their cause. German: "Ein Fehler in Zeile 30, Spalte 1, bedeutet meist, dass das Problem in Zeile 20 begann." Spanish: "Dos puntos faltantes en la línea 15 pueden no aparecer como error hasta la línea 22" (abacktools de/es, WebFetch, one source). So the test's `n = i + 2` (L173) is the test's own line number. 04/05 must not claim it matches PyYAML's error mark.
