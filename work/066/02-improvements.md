So `_run(wt, "check_pipeline.py")`, with `wt` a detached worktree of HEAD, needs no script change. Because the script still comes from `REPO`, an I2 who edits check_pipeline.py (uncommitted) still has the edit tested against every committed item, and an I3 mutation inside a scratch worktree still reaches it (`REPO` is that scratch tree). Keep `REPO / "scripts"` in `_run`. Do not switch to `wt / "scripts"`, or uncommitted script edits drop out of the test. Reasoning: L43-46, L359-366, L583.

Two pytest runs at once do not collide. Each gets its own `tmp_path` (R1 F10), and git keeps the admin names apart: the private directory is "the base name of the linked worktree's path, possibly appended with a number to make it unique ... (or `$GIT_DIR/worktrees/test-next1` if `test-next` is already taken)" [https://git-scm.com/docs/git-worktree]. So 065 and 066 running the suite in this tree at the same moment is safe. ## 3 ways AGAINST
1. **The test stops catching the running item's own gaps before commit.** Today it fails when the current item's own step file has no log line yet. Under B that is caught only by the explicit `python3 scripts/check_pipeline.py` run that run-item L14 and I3 already require (R1 F12). A committed red item that an uncommitted fix would turn green also stays red in the test until commit. That is correct "committed state" behaviour, but I2 may misread it. Mitigation: a docstring line, "checks HEAD's work/ and logs/; run `check_pipeline.py` in the tree for uncommitted files (item 066)". Keep the existing three asserts (exit 0, `RESEARCH CODE: none`, `061: complete`).
2. **Cleanup and repo side effects.** `git worktree add` writes `$GIT_DIR/worktrees/<name>` in the shared repo. `remove` "refuses to remove an unclean worktree unless `--force` is used" [https://git-scm.com/docs/git-worktree]. If pytest is killed mid-test, the entry stays until `git worktree prune` runs or `gc.worktreePruneExpire` passes (same page), and `git worktree list` shows a stale test tree. Mitigation: do the add/remove in a `try/finally` (or a fixture), and call `git worktree remove --force` in the finally. Use `NO_GIT` (tests L604) for the skip. Without git the test already fails today, because the script prints `RESEARCH CODE: not checked (no git)` (L650) and L143 fails. So a skip when git is missing changes nothing that used to pass, and if git is present but HEAD is missing the test should still fail loudly. Do not add a silent fallback to `REPO`: that brings back the cross-item failure without saying so.
3. **A full checkout costs time and disk on every run.** A full worktree checks out all of HEAD, including data/real/options/*.csv.gz and prices, earnings, dividends and splits for 21+ tickers (more than 100 files under data/, Glob). The cost is UNVERIFIED (no shell in R2). A lighter variant exists, but it is untested: `git worktree add --detach --no-checkout <wt> HEAD` and then `git -C <wt> checkout HEAD -- work logs`. The script reads nothing else from disk (FOR 1), and history checks use the object DB. `--no-checkout` exists "to suppress checkout in order to make customizations" [https://git-scm.com/docs/git-worktree]. Avoid `git sparse-checkout` here. In a linked worktree it may turn on `extensions.worktreeConfig` in the shared repo config (UNVERIFIED; my reasoning from git behaviour, not checked). Recommendation: I2 times the full checkout first (`pytest --durations=5`) and switches to the partial variant only if the test is clearly slow. In that case I2 must check that `git -C REPO status` and `git config --list` are unchanged afterwards.
