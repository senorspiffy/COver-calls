## Decisions on R1/R2 open points (with reasons)
- **D1 Placement and precedence (R1 OQ1, R2 FOR 2, AGAINST 3):** add `_frontmatter_error(front)` and call it in `agent_tools` right after `front` is taken (L109), before `_field`. It walks `front` in order and returns the first error. Within a line, the tab rule is checked first, then the quote rule. So a multi-line quoted `tools: "Read,` now gets the unclosed-quote text. No existing CASE has that shape (S2).
- **D2 Quote rule (R1 F14, R2 FOR 1):** use an escape-aware scanner, not `endswith` (#37). A1's two shapes are caught either way. The scanner also catches `"abc\"` and `'it''`.
- **D3 After the close (R2 Hole 2, 8):** only spaces, or one or more spaces followed by `#...`. A tab or any other text → error. This accepts `"x" # c` (R1 F15) and rejects a trailing tab (fails closed; 0 lines today).
- **D4 Tab rule (R1 OQ4, F11):** leading whitespace only. `tools:\tRead` stays valid. L54's `" \t"` is left unchanged: it is unreachable inside frontmatter after this change, and removing it changes no test result.
- **D5 Open `[`/`{` on other keys (R1 OQ2, F16): left out of 080.** It is outside the request, no probe has been run, and adding it changes j3's text (R2 AGAINST 3). The hole is real in kind: PyYAML's own test data says indentation "may be violated" in flow context (#16, #39). Proposed follow-up for the orchestrator to open: a BUG or EFFICIENCY item where A1 first probes `description: [a,` / `tools: Read` / `]` with PyYAML, then fails closed if needed.
- **D6 Line numbers:** `<n>` is the 1-based line in the file (front index + 2), so the first frontmatter line is line 2.
- **D7 No PyYAML** (#6, RI-008): no cross-check and no skip.
- **D8 No runtime claim** (#21, #29): the error text names the line and the shape. The docstring says the test cannot tell which tools such a file grants, so it is an error. Nothing says what Claude Code does.
