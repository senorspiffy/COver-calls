## 3 ways FOR
1. **Use an escape-aware quote scanner (R1 F14) on every frontmatter line, not A1's `endswith` rule.** The Chinese KCL YAML FAQ states the same escape rules R1 took from the spec: in double quotes `\"` escapes `"` and `\\` escapes `\`. A single `\` at the end of a line continues a double-quoted string. In single quotes `''` stands for one `'` ("使用两个单引号 `''` 转义单引号 `'` 字符") [https://www.kcl-lang.io/zh-CN/docs/user_docs/support/faq-yaml] (WebFetch). So `description: "abc\"`, `description: "abc \` and `description: 'it''` are all still open, and `endswith` reads all three as closed. The scanner rules:
   - Double quote: skip the character after each `\`. A `\` at end of line means the value is still open.
   - Single quote: `''` is a literal. A lone `'` closes the value.
   - After the closing quote, allow only whitespace or ` #...` to the end of the line. Anything else is an error.

   This covers both of A1's shapes and the three escape holes the request does not name. It fails closed. Each rule gets its own mutation, as R1 proposed.
2. **Fail closed, and don't imitate a reader, because YAML readers disagree on exactly this shape.** PyYAML's own test data accepts a quoted scalar whose continuation line starts at column 0, as a deliberate leniency: `bar: 'quoted scalars` / `may not adhere indentation'` (file `sloppy-indentation.data`) [https://flutter.googlesource.com/third_party/pyyaml/+/99d27e78e87838e96c4a859d3fb87e9d36407811/tests/data/sloppy-indentation.data] (WebFetch). In R2's reading of YAML 1.2.2, a block-mapping value sits at indent n+1, so a stricter reader could reject a1-n1 outright where PyYAML returns `['name', 'description']`. That reading is UNVERIFIED: R2 did not fetch the production or run any other reader. German and Korean sources say the same thing in general terms. "unterschiedliche YAML-Verarbeitungsbibliotheken in verschiedenen Programmiersprachen [liefern] unterschiedliche Ergebnisse" [https://www.computerwoche.de/article/2815752/so-umgehen-sie-yaml-probleme.html] (WebFetch). "서로 다른 언어로 이루어지면서 YAML를 처리하는 라이브러리를 이용할 경우, 가끔 결과가 일관적이지 않을 수 있다" [https://www.itworld.co.kr/article/3574085/] (WebFetch). Claude Code's own reader is not known (R1 F21). Whichever way it goes, a1-n1 means either "no tools key, so every tool is inherited" or "the file is skipped silently" (R1 F19, F20), and neither is "six tools". The only answer the test can defend is an error. That also supports R1 Open question 1: put the check in `agent_tools` on all of `front`, before `_field`, because the attack line is `description:`, which `_field` never reads.
3. **The tab rule (leading whitespace only) and the bare `-` fixture are cheap, and the sources back them.** Tabs in indentation are forbidden by the spec (R1 F11). Spanish: "La especificación de YAML prohíbe explícitamente los caracteres de tab como indentación" [https://abacktools.com/es/blog/how-to-detect-and-fix-yaml-errors] (WebFetch). Japanese: "インデントではタブは使えません" [https://scrapbox.io/PythonOsaka/YAMLについて] (WebFetch). A frontmatter reader in the wild rejects them too: Obsidian's thread reports "The new version rejects tabs used as indentation in YAML blocks", and a forum regular answered "Tabs in the frontmatter/yaml block produce errors" [https://forum.obsidian.md/t/yaml-parser-breakage-in-the-new-update-tabs-stop-working/29310] (WebFetch). Today 0 of 7 agent files and 0 of 33 CASES have a leading tab (R1 F5; the Grep of the test above), so the rule breaks nothing that exists. The bare `-` fixture (`tools:` / `  -` → `unparsed tools: entry '' (item 075)`, R1 F4) is one line. It turns M14 from green into a failure of a named test, which is P2's whole point.

## Holes to watch out for (summary)
1. **Escaped endings** (FOR 1): `"abc\"`, `"abc \` (backslash continuation, zh) and `'it''` are open. `"abc\\"` and `'it'''` are closed. Use the scanner, not `endswith`. Add a mutation where the scanner is replaced by `endswith`, so at least one escaped-end fixture fails.
2. **Text after the closing quote**: `"x" # c` is valid. `"Read", "Bash"` is not valid YAML as one value, and today it would not be caught on `description:`. Rule: after the close, only whitespace or ` #...`, otherwise an error.
3. **A quote inside a plain value** (`description: Use "this" agent`) must not be flagged. Apply the rule only when the value's first non-space character is `"` or `'`.
4. **Indented and nested keys**: Claude Code frontmatter may hold nested values (for example `hooks:`/`mcpServers:` mappings; whether agents accept these here is UNVERIFIED). Apply the quote rule to any line's value after `key: ` or `- `, whatever the indent, not only at column 0.
5. **Tab scope**: only leading whitespace (R1 F11). Keep `tools:\t Read` valid (L39). The `\t` in L54's `" \t"` becomes unreachable inside frontmatter. I1 decides whether to leave it or remove it, and should note the choice.
6. **Precedence and line numbers** (AGAINST 3): `j3_unclosed` must keep its text unless the plan changes it in the open. Say whether `<n>` counts from the file or from `front`.
7. **One positive fixture**: a closed quoted description with a colon inside (`description: "a: b"`) plus the six tools gives no error, so the check is shown not to block the quoting that sources advise.
8. **Trailing tab after a closing quote**: parsers differ (SnakeYAML #517). Rejecting it fails closed. I1 decides.
9. **No PyYAML and no runtime claim**: Claude Code's reading of a1-n1 and a1-n2 is UNVERIFIED. The error text should say the test cannot tell which tools are granted, and should not claim what Claude Code does.
10. **The Korean and German rows share one source article** (InfoWorld, translated). Count them as one source, not two.
