## Findings (one claim per line, each with [source URL] or UNVERIFIED)
Python and git facts
- `subprocess.run`: "If *encoding* or *errors* are specified, or *text* is true, file objects for stdin, stdout and stderr are opened in text mode using the specified *encoding* and *errors* or the io.TextIOWrapper default." `CompletedProcess.stdout` and `.stderr` are each "A bytes sequence, or a string if run() was called with an encoding, errors, or text=True" [https://docs.python.org/3/library/subprocess.html]. So stderr is decoded with the same strict codec as stdout. This is why git echoing a `\xff` byte in its error message crashes `_git` even though the script never reads stderr (07 point 5).
- The `errors` parameter has been on subprocess since 3.6 ("Changed in version 3.6: Added the *encoding* and *errors* parameters") [https://docs.python.org/3/library/subprocess.html]. That is below the project's declared minimum of 3.10 (RI-008), so `errors=` is safe to use.
- Codec error handlers [https://docs.python.org/3/library/codecs.html]:
  - `'strict'`: "Raise UnicodeError (or a subclass), this is the default."
  - `'replace'`: "On decoding, use � (U+FFFD, the official REPLACEMENT CHARACTER)."
  - `'backslashreplace'`: "On decoding, use hexadecimal form of byte value with format \xhh."
  - `'surrogateescape'`: "On decoding, replace byte with individual surrogate code ranging from U+DC80 to U+DCFF. This code will then be turned back into the same byte when the 'surrogateescape' error handler is used when encoding the data."
- `Path.write_text` / `read_text`: "The optional parameters have the same meaning as in open()" [https://docs.python.org/3/library/pathlib.html]. `open()`'s default for `errors` is strict. That default is from my knowledge of the open() docs, not fetched: UNVERIFIED. If it holds, `surrogateescape` is the wrong choice here. `open_branches` L694 writes `_git` output back with `write_text(..., encoding="utf-8")`, and a lone surrogate cannot be encoded to UTF-8 under strict, so the crash would only move from `_git` to L694. U+FFFD from `'replace'` encodes in UTF-8. This is my reasoning from the two handler descriptions above.
- When stdout is not UTF-8 (for example an ASCII-only locale), printing U+FFFD could raise UnicodeEncodeError. UNVERIFIED (the sys.stdout encoding text was not in the part of https://docs.python.org/3/library/sys.html I could read). That only matters if the new "not checked (git failed: <stderr>)" text echoes git's stderr. Option: print it with `ascii()` or `errors="backslashreplace"`, or leave stderr out.
- git `die()`: "is for fatal application errors. It prints a message to the user and exits with status 128". `usage()` "exits with status 129". `error()` "returns -1" and does not exit [https://www.kernel.org/pub/software/scm/git/docs/technical/api-error-handling.html]. So 128 is git's documented "fatal" code. A1's malformed-shallow run got exit 128 from the shallow flag (logs/audit/2026-11-19-079.md L25/L61).
- `git rev-parse --verify -q`: "Do not output an error message if the first argument is not a valid object name; instead exit with non-zero status silently" [https://git-scm.com/docs/git-rev-parse]. The docs give no separate exit code for "no such ref" versus "git died", so a non-zero `--verify -q` exit alone cannot tell "no origin/main" apart from a broken repo (UNVERIFIED whether the codes differ in practice).
- `git cat-file -e`: "Exit with zero status if <object> exists and is a valid object. If <object> is of an invalid format, exit with non-zero status and emit an error on stderr" [https://git-scm.com/docs/git-cat-file]. Here too, missing and failed are both just "non-zero". It cannot be the only test of "path not in HEAD" when git may be dying.
- `git ls-tree`: without `-z`, "pathnames with "unusual" characters are quoted as explained for the configuration variable core.quotePath" [https://git-scm.com/docs/git-ls-tree]. The page states no exit status for a path that matches nothing: UNVERIFIED. The tree's existing 077 check relies on it: `uncommitted_steps` L499-502 lists `ls-tree -r --name-only HEAD -- work/` once, uses exit 0 + list as "committed", and treats a non-zero exit as an error.
- `git blame --line-porcelain`: the line content "is output after the above header, prefixed by a TAB", with committer fields "similarly" to `author-time` [https://git-scm.com/docs/git-blame]. The page does not say what blame does for a path not in HEAD. A1's note that it fails (logs/audit/2026-11-19-079.md L106) is not in the docs: UNVERIFIED by doc. It is A1's observation.
- The shallow file "tells Git to pretend as if they are root commits", and each line holds one object name [https://git-scm.com/docs/shallow] (quoted and R3-checked in work/079/01). A bad line makes git `die("bad shallow line")` (079 row 23, reproduced by A1 on git 2.43.0).
