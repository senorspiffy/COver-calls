## Findings (one claim per line, each with [source URL] or UNVERIFIED)

### A. How pytest names a test (the target the census must match)
1. On the command line a test is named by the module path, then `::` and the function name, with "parameters from parameterization enclosed in `[]`". Example: `pytest tests/test_mod.py::test_func[x1,y2]`. [https://docs.pytest.org/en/stable/how-to/usage.html]
2. Every test gets a unique nodeid "rooted at the `rootdir`", and `config.rootpath` is "used as a reference directory for constructing test addresses". [https://docs.pytest.org/en/stable/reference/customize.html] In this repo, pyproject.toml L19-21 sets `testpaths = ["tests"]` and `pythonpath = ["tests"]`, with the rootdir at the repo root, so collected ids read `tests/test_pipeline_check.py::...`. SITE_ROWS kills read `test_pipeline_check.py::...` with no `tests/` prefix (L6088-6089). A collection-based check has to map one form onto the other. (Repo files; the exact printed prefix is UNVERIFIED until I2 runs it.)
3. `pytest.mark.parametrize` "has the same signature as pytest.Metafunc.parametrize()". [https://docs.pytest.org/en/stable/reference/reference.html]
4. The `ids` parameter of `Metafunc.parametrize` takes a "Sequence of (or generator for) ids ... or a callable". "``None`` means to use the auto-generated id". "If no ids are provided they will be generated automatically from the argvalues". Parts of an id are "joined with dashes ("-")". [https://raw.githubusercontent.com/pytest-dev/pytest/main/src/_pytest/python.py] (This is the pytest main-branch docstring. The installed pytest version is not pinned: pyproject.toml L13 has `dev = ["pytest"]`. Whether the installed version behaves the same is UNVERIFIED.)
5. When ids repeat, pytest changes them: "The counter suffix is appended only in case a string wouldn't be unique otherwise", from `IdMaker.make_unique_parameterset_ids`. The format is `<prm_1_token>-...-<prm_n_token>[counter]`. Stacked parametrize calls are "Joined with "-"" in the item's `[..]` suffix. [https://raw.githubusercontent.com/pytest-dev/pytest/main/src/_pytest/python.py] So the id written in `ids=[...]` is not always the final collected id. Only collection gives the final id.
6. Stacked `parametrize` decorators give "all combinations", in "the order of the decorators". [https://docs.pytest.org/en/stable/how-to/parametrize.html]
7. "pytest by default escapes any non-ascii characters used in unicode strings for the parametrization". [https://docs.pytest.org/en/stable/how-to/parametrize.html] So a non-ASCII id in source text would not equal its collected id. Every SITE_ROWS id today is ASCII (L6090-6132, read).
8. ids can come from a list, from a callable, or from `pytest.param(..., id=...)`. The `--collect-only` example output shows the ids each form produces (`test_timedistance_v1[forward]`, `test_timedistance_v0[a0-b0-expected0]`). [https://docs.pytest.org/en/stable/example/parametrize.html]
9. `pytest --collect-only -q` writes a file that can be passed back to pytest as test arguments, so `-q` collection lists one test address per line. [https://docs.pytest.org/en/stable/how-to/usage.html] (How the trailing "N tests collected" line looks is UNVERIFIED. I2 has to parse only lines that contain `::`.)
10. Exit codes: 0 "All tests were collected and passed successfully"; 2 "Test execution was interrupted by the user"; 3 "Internal error ... or a plugin raised while importing"; 4 "usage error ... a `conftest.py` that fails to import"; 5 "No tests were collected". [https://docs.pytest.org/en/stable/reference/exit-codes.html] So a collection subprocess has to assert exit 0. Any other exit code must fail the census and never pass it by default (RI-002). Whether a collection error gives code 2 is UNVERIFIED; the docs text for 2 says only "interrupted by the user".
11. In-process collection is discouraged. Calling `pytest.main()` imports the tests, and "subsequent calls to `pytest.main()` from the same process ... will not reflect changes to those files between the calls ... is not recommended". [https://docs.pytest.org/en/stable/how-to/usage.html] A subprocess avoids this.
12. Reading marks from the function object is not a documented public route. The docs cover `pytestmark` only as a module global ("use the pytestmark global variable") and as a legacy class attribute. Plugin code reads marks with `item.iter_markers(...)`, which needs a collected item. [https://docs.pytest.org/en/stable/example/markers.html] A function-level `pytestmark` list (what `@pytest.mark.parametrize` stores on the function) is therefore UNVERIFIED as stable API.
13. Precedent in this repo: tests/test_stale_bytecode.py L12-25 (item 107) already runs `sys.executable -m pytest -q -p no:cacheprovider` as a child process. It strips `PYTEST_ADDOPTS`, `PYTHONSAFEPATH` and the bytecode variables, and sets `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1`. A1 resolved the 33 kills against `pytest --collect-only` by hand (583 ids, logs/audit/2026-11-26-109.md L32-34). A1's 066 audit used `--collect-only -q` (logs/audit/2026-11-15-066.md L40).

### B. What ast can and cannot resolve (for an ast-only option)
14. `ast.literal_eval` accepts "only ... strings, bytes, numbers, tuples, lists, dicts, sets, booleans, `None` and `Ellipsis`". It is "not capable of evaluating arbitrarily complex expressions" and has "no name lookups". [https://docs.python.org/3/library/ast.html]
15. Seven of the eight parametrized kill tests pass `ids=` as a literal list: L4576, 4621, 5268, 5295, 5351, 5716, 6071. `test_from_cutoff_boundary` (L6025) passes `ids=FROM_IDS`, and FROM_IDS is a list comprehension at L6022. By finding 14, `literal_eval` cannot resolve that Name. 11 of the 33 checked kills use that test (S2 x2, S4 FROM, S5 x2, S6 x2, S10 x2, S14 x2; counted from L6093-6124). So an ast-only check without evaluation misses a third of the kills.
16. Kill count, computed from SITE_ROWS L6090-6132: 34 kill strings, minus 1 EQUIVALENT, leaves 33. Of these, 23 have a `[<id>]` part (11 on test_from_cutoff_boundary, 2 rule_gate, 2 batch_strict, 1 stray_round, 1 read_or_unnamed, 2 round_build, 2 scratch, 2 batch_log). 10 name a non-parametrized test (S1 x2, S3 x2, S4 FROM-1, S8 FROM-1, S15 x2, S17 x2). 23 + 10 = 33, which matches A1's "all 33".
17. Exact-match collection also catches a case the current check misses: a kill with no `[...]` on a test that is parametrized. pytest gives that test only bracketed ids (findings 1 and 4), so `file::test` alone is not a collected id. (This follows from the docs; a probe is UNVERIFIED until I2 runs one.)

### C. S7 FROM-1 equivalence (the premise a behaviour test must pin)
18. The site, scripts/check_pipeline.py L1089-1090: `if "I2" in bad and int(item_dir.name) >= TIMED_FROM \` / `and all(log_fields_ok("I2", m[4], m[5], timed=False) for m in own_i2)`. `bad` (L1084-1085) holds the agents whose own lines fail `log_fields_ok(m[3], m[4], m[5])` with default `timed=True`. `own_i2` (L1087-1088) holds the same item's own I2 lines.
19. `log_fields_ok` (L845-850): `timed` is read only at L848 (`agent == "I2" and timed and int(item) >= TIMED_FROM`). At ID 089, which is TIMED_FROM - 1 (TIMED_FROM = 90, L458), L848 is false for both `timed` values. So `log_fields_ok("I2","089",f) == log_fields_ok("I2","089",f,timed=False)` for every field f. If "I2" is in bad, some own I2 line fails, the `all(...)` is False, and the gate is not entered. The S7(b) mutant (`>= TIMED_FROM - 1`) changes the condition only for ID 089, so it cannot change any output. This repeats 05/06 and A1's re-trace (logs/audit/2026-11-26-109.md L25-27). S7(b) run: `581 passed` (work/109/05-build-report.md L77).
20. What would break the equivalence: anything that makes `timed` matter below TIMED_FROM, for example L848 losing its `int(item) >= TIMED_FROM` term, or L1090 calling `log_fields_ok` with other arguments. Today no test fails when that happens together with S7(b). The census only requires the EQUIVALENT text to exist (L6171-6172).
21. The fixture helpers support ID 089. `_timed_repo(tmp_path, rules, item=..., i2=...)` (L4538-4550) calls `_suite_item`, and `_suite_item` replaces the line `12:00 | I2 | {item} | {FIELDS['I2']}` (L3724-3725). `_item` writes `_field('I2', item)`, which is `FIELDS['I2']` for every ID >= 76 (L32-34), so `assert old in text` holds at 089. (Read from code, not run. RI-001 / A1 follow-up 4: I1/I2 must run the fixture at 089 once before FIT.)
22. A differential run is possible. check_pipeline.py imports only the standard library (L424-430) and is run as a script with cwd set to the fixture repo (`_run`, L74-77). A copy with the one S7(b) edit can be run from a tmp dir against the same fixture, and the two stdouts compared. The search string `>= TIMED_FROM \` (with the backslash) appears only at L1089; L1121 ends `>= TIMED_FROM:` (grep). Stale bytecode (RI-015) does not apply to the copied script: Python "always recompiles and does not store the result for the module that's loaded directly from the command line". [https://docs.python.org/3/tutorial/modules.html]

### D. Alias and attribute uses (follow-up 3)
23. `ast.Name` "A variable name. `id` holds the name as a string, and `ctx` is one of" Load/Store/Del. "Variable references are given a context to distinguish these cases". `ast.Attribute`: "`attr` is a bare string giving the name of the attribute". `ast.walk` yields every descendant "in no specified order". `ast.Compare` holds `left`, `ops` and `comparators`. [https://docs.python.org/3/library/ast.html]
24. So a use census can be built from ast alone. Take every `ast.Name` with `id.endswith("_FROM")`, `id != "UNTRACKED_FROM"` and a Load ctx that does not sit inside an `ast.Compare`, plus every `ast.Attribute` whose `attr` ends `_FROM`. The expected result is empty. Module-level definitions such as `SUITE_FROM = 87` (L447-517) are Store, so they drop out. `_rule_seen(..., "TIMED_FROM", ...)` passes the name as a string constant (L1091 etc.), so it drops out too. A1's alias (`c = SUITE_FROM`) is a Load outside a Compare, and `cp.SUITE_FROM` is an Attribute; both would be reported. [https://docs.python.org/3/library/ast.html]
25. Today's count is expected to be 0. A grep of non-comparison `_FROM` tokens in code lines (not docstrings) of scripts/check_pipeline.py shows only definitions (L447-517), `UNTRACKED_FROM` uses (L543, 1845, 1940, 1968, 2058, 2239) and string arguments. This matches A1's probe ("0 new keys for both", logs/audit/2026-11-26-109.md L78-81). The 0 is a reading of grep output, not an ast run, so it is UNVERIFIED until I2 runs it (RI-001).
26. Known limit, also from the ast docs: `ast.parse` "won't do any scoping checks" [https://docs.python.org/3/library/ast.html]. So a local variable or parameter that happens to be named `X_FROM` would look the same as the global constant. A check that flags every such Load is the conservative direction: it gives false alarms, never a silent pass.
