## Question
How should `scripts/check_pipeline.py` read I3's verdict in `06-verification.md` so that an item whose latest I3 round is FAIL prints an `I3 FAIL` status, and a later PASS round clears it? This should work the way 07's `A1 result:` line already does (item 042). It must handle 06 files with round headers (069, 070, 002, 061, 062) and older 06 files with one verdict. What do the current files actually contain, where would the check go, and which choices are left for R2/R3?

Sources are mostly repo files, cited as path:line as of 2026-11-18 on branch daily-fixes/2026-11-18. There is one official Python doc URL. I read the files and did not run any code (no shell). Every "today" result below comes from reading grep output, not from running the script.

## Findings (one claim per line, each with [source URL] or UNVERIFIED)

### How the script decides status now
1. `classify()` reads 06 only to check that it exists. It finds no verdict in it. Its only verdict reading is the `A1 result:` lines of 07 [scripts/check_pipeline.py:302, 315-323].
2. When 01-06 are present and 07 is absent (FULL), `classify()` falls through to `return "in progress", f"{scope}: next {need[len(have)]}"`, which prints `in progress (FULL: next 07)`. An I3 FAIL therefore cannot be told apart from "I3 not yet written its 07" [scripts/check_pipeline.py:324].
3. A1 FAIL (item 042) works like this. `re.findall(r"^A1 result:\s*(\w+)", ..., re.M)` runs over 07, and the last match decides: FAIL gives `"A1 FAIL"` with detail `sent back, needs a later A1 PASS line (item 042)`. Items with no line (outside PRE_A1_LINE) are `awaiting A1` [scripts/check_pipeline.py:317-323].
4. `main()` puts A1 FAIL items in `failed`, prints `A1 FAIL: <ids or none>`, and `failed` makes the exit code 1 [scripts/check_pipeline.py:810-811, 841, 859].
5. The docstring lists the statuses. A1 FAIL is described as "the item went back to the team and is not complete until a later PASS line (exit 1)". There is no I3 entry [scripts/check_pipeline.py:20-33].
6. With `re.M`, `^` matches at the start of each line [https://docs.python.org/3/library/re.html]. `re.findall` scans left to right and returns matches in the order found, so `[-1]` is the last line in the file [https://docs.python.org/3/library/re.html].
7. The `IN PR` override applies only to `STUCK`, `not started` and `in progress`. A new I3 status would not be replaced by `IN PR` unless it is added to that tuple [scripts/check_pipeline.py:796-802].
8. On open branches, `open_branches()` runs `classify()` on the branch's files but reports only `SKIPPED` (as BRANCH SKIPPED). A1 FAIL on a branch is not reported today, and an I3 FAIL would not be either [scripts/check_pipeline.py:486-488, 838-840].
9. `_open_at()` (item 053) treats an item as open when its 07 is absent, has no A1 line, or its last A1 line is FAIL. An item whose 06 is I3 FAIL and has no 07 is already open there, so 053 is not affected [scripts/check_pipeline.py:508-518].

## Open questions
1. **Which verdict line counts?** (a) The first `^Verdict:` line, which is the template rule that line 2 shows the latest round (finding 15). This works for 061/062, whose later rounds have no Verdict line (finding 20). (b) The last `^Verdict:` line. This breaks if a later round has no Verdict line and the stale round-1 line is last. (c) Read line 2, and also check that it agrees with the last `Verdict:` line when the two differ in the first word (gives INCOMPLETE, catching an un-updated summary). All three give PASS on today's 67 files (findings 16, 18).
2. **Verdict regex.** It must be anchored (`^`, re.M) and allow `**` bold (finding 21). It must take only the first word, so a FAIL inside the parentheses is not read (finding 22). It must reject the unfilled template `PASS | FAIL` (finding 23). It needs negative tests for each, under the RI-012 rule (.claude/agents/i3-verifier.md:14), plus one for a mid-line `Verdict:`.
3. **"sent back to <step>".** The target is only in prose (finding 25), and parsing it would be another free-text classifier (RI-012). Options: (a) add it to the template verdict line, e.g. `Verdict: FAIL (round <n>; sent back to I1|I2|I1 I2; ...)`, and read only that field; (b) print `I3 FAIL (sent back: see 06 Sent back section)` with no parsed target. A FAIL with no stated target must never default to I2 (RI-002); it should print "target not stated" or be INCOMPLETE.
4. **Order with A1 FAIL.** Should an I3 FAIL in 06 win over an A1 FAIL in 07 (finding 28)? This repo has no timestamps across files short of git. One rule that fits run-item: a FAIL in 06 means the current build has not passed I3, so any A1 line refers to an earlier build, and the I3 check runs first.
5. **Exit code.** The request says "like `A1 FAIL:`", which means exit 1. That keeps the repo test red between I3's FAIL and the next PASS, as A1 FAIL did (finding 31). Should it be exit 1, or listed like `AWAITING A1` (exit 0)?
6. **06 with no readable Verdict line.** None exists today (finding 14), but fixtures have none (finding 29). Options: UNKNOWN as INCOMPLETE from a cutoff ID (like CHECKLIST_FROM / WHOLE_DIFF_FROM), with older items not re-checked; or treat it as not FAIL. Treating it as PASS silently would be RI-002.
7. **Branches and IN PR.** Should an I3 FAIL on an open branch be reported (finding 8)? Should it count for the IN PR override (finding 7)?
8. **Cross-check with the I3 log line.** The last `| I3 | <ID> |` log line already says PASS/FAIL in a checked format (finding 13). Should a disagreement between it and 06 be flagged?
9. **Agent text.** i3 step 5 says "On PASS, write 06" (finding 26). Should it say that 06 is written on FAIL too, with the verdict line updated, so the check always has a file to read?
10. Fixture tests to write, from the request: FAIL with no 07 gives `I3 FAIL` and the summary line; FAIL then a PASS round (line 2 updated) clears it; an old single-verdict 06 with no round header is unchanged. Add the negatives from Q2.
