## 3 ways FOR
1. **Take R-A as written. YAML's continuation threshold for a plain scalar item is the dash column for both indent forms, so one rule covers F-1 form 1 and form 2. Keep g3 as the RI-012 negative, because a tutorial shows exactly that shape loading.**
   - Basis: R1 F14-F15, from the PyYAML scanner. A plain scalar continues on a later line at column ≥ `self.indent + 1`. For an indented sequence, `indent` is the dash column (`add_indent(self.column)` in `fetch_block_entry`). For an indentless sequence under `hooks:` at column 0, `indent` stays at the parent key's column, which is also the dash column (0). So "ind > last dash column" is the threshold in both cases. R2 trace (not run): g1 `- a` / `  b: c` has 2 > 0 and g2 `  - a` / `    b: c` has 4 > 2, so both go to the existing continuation branch and get VALUE (L336-L338). That is the same error the test already gives for the measured ScannerError on a key continuation (c4, R1 01 L57).
   - Mandarin evidence for the negative fixture g3: runoob's YAML intro gives `- newline` / `  newline2` with the note "字符串可以拆成多行，每一行会被转化成一个空格" [https://www.runoob.com/w3cnote/yaml-intro.html] (WebFetch). That is g3's shape (a scalar item, then a line at its content column). The tutorial reads it as one string, not as a new node. 2. **Widen R-A for scalar items that cannot continue: a closed quoted or flow value, or a plain value ended by ` #`. Any non-comment line deeper than the dash is a named error, colon or not. Without this, R-A's "it is a continuation" reading is wrong for those items, and `- "a"` / `  b` and `- a # c` / `  b` keep returning a tool set.**
   - Japanese evidence, measured by the author: a scalar item ended by a comment is not continued by the next deeper line. This matches R1 F14: `scan_plain` stops at `self.peek() == '#'`.
   - R2 reading (not run) of R1 F19 for the no-colon case. In `hooks:` / `- a # c` / `  b` / `tools: Read`, the scalar `a` has ended, so `b` is a new SCALAR token where the block sequence expects BLOCK-ENTRY or BLOCK-END, and that gives a ParserError. In the continuation branch, `if no_cont and not in_flow:` return a named error, e.g. "line after a closed item value on frontmatter line {n} (item 111)" (R3 picks the text). Fixtures: g5 `_fm("hooks:", "- a # c", "  b", TOOLS)` and g6 `_fm("hooks:", '- "a"', "  b", TOOLS)` give the new error. g4 then gets the new text instead of VALUE, which is the more truthful message. Lines under `tools:` stay with `_field` (`in_flow`).

2. **R-A's stated reason ("a line past the dash continues the scalar") is false for quoted, flow and comment-ended items. Documenting it as written repeats RI-002 at the docstring level.**
   - The qiita case in FOR 2 shows that a comment ends the scalar, so the next line is a new node, not a continuation. Under R-A as written, g4 (`- "a"` / `  b: c`) gets VALUE, which is fail-closed. But g6 and g5 (no colon) pass with a tool set while YAML is predicted to raise (R2 reading of R1 F19, UNVERIFIED). R1's g4 note ("YAML is predicted to raise") is right about the verdict but not about the mechanism.    - If FOR 2 is not taken, the "Item 111:" docstring paragraph must say R-A applies to plain scalars not ended by ` #`. It must also list `- "a"` / `  b` and `- a # c` / `  b` under "Not checked", or the test again has an undocumented pass of the kind F-1 was.
3. **R-B/R-C add per-level state whose hardest cases are hand traces only, and three existing interactions can flip results.**
   - (a) Column 0 is both a map level (`hooks:`) and an indentless-sequence level (`- x`). R-B must not fire on `a: v` after `- x` at column 0 (k5, v19, nk6, valid by R1 F19-F20). R2 trace (not run): under that wording, k5 gives a false R-B error. The spec needs an explicit rule, for example "a level keeps the kind of the line that first opened it, until it is popped".

Add k7 `_fm("hooks:", "  -", "    a: b", "    c: d", TOOLS)` → pass (predicted to load, UNVERIFIED).
   - (c) The test cannot measure libyaml where CSafeLoader is absent (106 container, work/106/02-improvements.md L46). The "both loaders" claims for k1-k7, g1-g6 stay predictions unless I2/I3 prints `yaml.__with_libyaml__` True. The measured pair is only er1 (106/05) and D3, F-1 (A1).
