---
description: Run one work item through Research -> Implementation -> Audit
argument-hint: <work item ID>
---
Run work item $ARGUMENTS through the pipeline, one agent at a time, in this order:
r1-researcher -> r2-improver -> r3-fact-checker -> i1-reviewer -> i2-builder -> i3-verifier -> a1-auditor (per-item mode).

If `request.md` says `Scope: RESEARCH ONLY`, stop after r3-fact-checker: R3 writes `work/$ARGUMENTS/07-audit-task.md` (what A1 should check in 01-03), then run a1-auditor (per-item mode). Missing 04-06 files are expected for these items. If there is no Scope line, treat it as FULL. A RESEARCH ONLY item writes no code (ccbot/, scripts/, tests/, config/, or a `.py` file under work/<ID>/; item 064). Research that needs code is FULL, or the person waives 04-06 with `Waived: 04 05 06 (person, <date>: <why>)` (item 062).

If `request.md` says `Scope: FAST (person, <date>)` (the person asked to go faster), R2 and I1 may be skipped; R3's fact check and I3's verification never are. Nobody else may shorten the pipeline: `check_pipeline.py` reports any other FAST line as SKIPPED (item 042). A step that is waived after the fact is listed on a `Waived: <steps> (<who>, <date>: <why>)` line in request.md, which the person sees in review. Only the person may waive 03 or 06 (`<who>` = `person`); `scripts/check_pipeline.py` reports any other waiver of them as SKIPPED (item 031).

Fix branches never edit `logs/recurring-issues.md`; guardrail status goes in 05/06 and A1 copies it on main (item 036). If `git rev-parse --is-shallow-repository` prints true, run `git fetch --unshallow`, then test again. If it is still true, report UNTRACKED CHANGE, RESEARCH CODE, REAL-DATA FIELD, LOG TIME, MAIN AHEAD, OPEN BRANCHES and RULE NOT SEEN as 'not checked', never 'none' (items 079, 084, 090). Before starting, run `python3 scripts/check_pipeline.py` after `git fetch origin`: if the item is IN PR, or a file you will change is on an OPEN BRANCH, build on top of that branch (item 034). If it prints a `RULES BRANCH:` line, build on top of that branch too, even when you change none of its files: it changes the rules your item is built under (item 049).
If an urgent fix goes on main while `RULES BRANCH:` is not `none`, its 05 says so and names that branch (item 084); `RULE NOT SEEN:` will then list it once the branch merges main, if it fails a rule it never saw.

Before each step, confirm the previous step's file exists in work/$ARGUMENTS/. No file for the person (a summary, a screen, a code change) is written or merged before the step that checks it. At the end, run `python3 scripts/check_pipeline.py`: the item must not show SKIPPED or INCOMPLETE, and `LOG TIME:` must not name it, and `LOG BATCH:` must not name it (item 086) (every log line is written with `check_pipeline.py --log` as soon as its step's file exists, never in a batch at the end, item 045; I3's 06 has the `Recurring issues checked:` line, item 043). If a step returns BLOCKED, NOT A FIT, or FAIL, send the item back to the step named in that file and continue from there. Stop after 3 loops on the same step and report to the person.

Log lines and check_handoff (item 072). R1, R2, R3 and I1 have no shell (no Bash on their `tools:` line), so the orchestrator runs their commands; I2, I3 and A1 run their own. For each R1, R2, R3 and I1 step, in this order, one step at a time and never in a batch across steps or parallel items: (1) the step's file exists; (2) after R1 and R3, run from the repo root (both scripts use paths relative to it) `python3 scripts/check_handoff.py <ID>`; after R3, paste its output into 03 under the template's `check_handoff output (run by the orchestrator <YYYY-MM-DD> <HH:MM> UTC, exit <n>; must say PASS):` line. After R1, take only the `sources count` line; its exit code does not gate R1 (an old 03 from an earlier loop is R3's to fix); (3) if it printed FAIL, write no log line and do not commit 03: send the item back to R3 with the output (one loop on R3); (4) run `python3 scripts/check_pipeline.py --log <agent> <ID> "<fields>"`, copying R1's count from `sources count`, R3's from `totals line` (as-is → verified) with READY/BLOCKED from 03's Status line, and R2's and I1's fields from the text after `Log fields: ` on the last line of 02/04, unchanged; (5) commit the step file and its log line. The commit that adds a step's log line has the subject `Item <ID>: ` followed by the line `--log` printed for that step, copied unchanged, never reworded (item 082); a commit made before that step's `--log` line has no such subject rule. The orchestrator never writes to logs/ itself and never edits a refused line: a `--log` refusal (exit 2) goes back to the step. `--log` also refuses while a later step file (01-06) of the same item exists (item 086). After a send-back (R3 BLOCKED, I1 NOT A FIT, I3 FAIL, or `A1 result: FAIL`) it refuses a step after the sender until the sender logs again, a step before the sender once the sender's file no longer shows its send-back verdict, and any line after a later step of the same round (item 090): log each step before the next one runs.

A follow-up to a completed item (its 07 has `A1 result: PASS`) is a new item, never a note in the old item's files (item 053). I2 commits each code change together with its 05 change. Its commit that adds the I2 log line follows the same subject rule (item 082). A diagnostic `.py` under work/<ID>/ is code too: commit it together with that item's step file (item 064). PRs are merged with "Create a merge commit", never squash or rebase: the item-053 cutoff must stay in main's history. `check_pipeline.py` must not print an `UNTRACKED CHANGE:` entry.

When an item changes `ccbot/realtest.py`, iterate with `python3 -m ccbot.realtest --tickers <affected> --out <scratch>` (SPY is added automatically; never the default `--out`, which overwrites the published reports/real/ with a partial set), and run the full backtest (no `--tickers`, `--out <scratch>`) once per step that publishes numbers; a full run made at another commit counts as the base only if `git diff --stat <that commit> <base> -- ccbot/ config/` is empty and both used the same data, because walk-forward, Monte Carlo, period, BXM-vs-SPY and fits_3k come only from the full run (item 068). I3's head run is always its own full run, made for 06 with its own scratch `--out`, for every item whose 06 needs the Real-data TOTAL line (TRIGGER and TRIGGER_DIRS in scripts/check_pipeline.py): never give I3 the head run made for 05, even when the same-inputs check passes, and if I3's run is cut off, I3 runs it again; only a base run may be reused (item 073). Every agent works in its own new scratch dir, made with `python3 -c 'import tempfile; print(tempfile.mkdtemp(prefix="<agent>-<ID>-r<round>-", dir="<absolute scratchpad path>"))'`, and never reuses or writes into another agent's dir, even for the same item; agents with no shell (R1-R3, I1) get theirs from the orchestrator (item 091).
