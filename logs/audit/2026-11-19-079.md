## Findings
- **P1 (proposed BUG, to R1): a git failure is read as "nothing found" in LOG TIME, OPEN BRANCHES and --next-id.**
  - Evidence, from the clone at 2977b96 with `.git/shallow` = a15129c + `zz` (so every git call dies with `bad shallow line`):
    - (a) A scratch commit added a late log line `23:59 | I3 | 079 | ...`. The full clone printed `LOG TIME: 079 I3 (2026-11-20 23:59 after commit 2026-11-20 02:25 UTC)`, exit 1. The malformed-shallow run printed `LOG TIME: none`.
    - (b) A scratch unmerged ref `origin/scratch-x` added work/099. The full clone printed `OPEN BRANCHES (not merged into HEAD):` and `--next-id` gave `100`. The malformed-shallow run printed no OPEN BRANCHES line, and `--next-id` gave `080`. That ID would clash with the branch's next item (RI-009, item 037).
    - Both scratch refs and commits were removed afterwards.
  - The run still exits 1 through the 077 and INBOX lines, so the run as a whole is not a pass. But each of those lines reads as a clean answer.
  - Root cause: `late_log_lines` L601-602 (`if out is None or out[1] != 0: continue`), `open_branches` L638-639 (`return []`) and `next_id` L983-984 (`out[1] == 0 else []`) each map a failed git command to an empty result (RI-002 family). The trigger is a clone-state failure (RI-014 family). 079 fixed only the walk users.
  - Note on intent: blame of a log file that is not committed fails too, so `late_log_lines` must keep skipping that case. It needs a check that tells "path not in HEAD" apart from git dying.
  - Proposed guardrail:
    - One helper `_git_ok(...)`. When `rev-parse HEAD` itself fails while `--show-toplevel` succeeds, it makes every git-reading line print `not checked (git failed: <first stderr line>)`, and `--next-id` exits 2.
    - A test with a malformed `.git/shallow` pins LOG TIME, OPEN BRANCHES and `--next-id`.
    - A mutation that restores `continue` / `return []` fails that test.
  - Proposed recurring-issues link: RI-014, new occurrence 2 (2026-11-20, found by A1 before merge), and RI-002 cross-reference. A1 daily commit on main to confirm; this file does not edit recurring-issues.md.
- **P2 (proposed BUG, to R1, can be folded into P1): `_git` crashes on non-UTF-8 git output.**
  - Evidence: 07 point 5. A `\xff` byte in `.git/shallow` gives a `UnicodeDecodeError` traceback, exit 1. It also crashes on 7b09a8a.
  - Root cause: `_git` L627 `text=True, encoding="utf-8"` with strict errors, and git echoes the bad byte in stderr.
  - Guardrail: `errors="replace"` in `_git`, plus a test that writes a `\xff` shallow line and expects the `not checked (shallow clone; ...)` lines with no traceback.
