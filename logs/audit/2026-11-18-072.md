## I3's three points (07), judged
1. **x2, the substring rule:** confirmed. A line that tells the agent to run the script itself passes if it also contains the word "orchestrator".
   - A1's judgement: not a defect, and not on its own worth an item. Our own agents and the I1-I3 review write these lines, not untrusted text, and the test's job is to catch drift back to the old wording, which m1 shows it does.
   - I3 is right that RI-012 (item 059) does not apply. That rule covers code that classifies an error or reply by text; this test lints rule text.
   - A cheap tightening (the line must contain "the orchestrator runs" or "the orchestrator copies", or the file must also say "you run no command") can ride along with P1. It is optional.
2. **x1, the inline YAML list:** confirmed, and **wider than reported.**
   - I3 says it "fails loud". That holds only when the file already has Bash (i2, x1).
   - On a no-shell file, the flow list parses into the tokens `[Read` ... `Bash]`. `Bash]` is not `Bash`, so the file still counts as no-Bash, its lines all hold "orchestrator", and the set assert sees the same four stems.
   - So a Bash grant to r1 passes all 7 tests (x4). This is exactly the change the set assert exists to make visible (04 Guardrail tests: "a newly shell-enabled one is a visible RULES change").
   - Root cause: the parser silently drops any token it does not recognise, so "could not parse" becomes "not Bash". That is the RI-002 shape (uncomputable input turned into a value), here in a test helper.
   - Proposed as P1 (BUG). It does not fail 072. The drift test is an extra the request did not ask for (03 D5), the four real files use the comma form today (all 7 have one-line `tools:` values, and the test passes), and the rule text itself is correct.
3. **I2's `tests 411/411`:** a wrong count.
   - The suite at bb5a32e collected 412 tests: 411 passed and 1 skipped (05, 06, and 404 + 7 + 1 skip).
   - In every other full-suite I2 line A1 read (061, 063, 064, 066-070, 073), `<total>` is larger than `<pass>`. Where A1 can check the split, the difference is the skip: 064's line says `316/317 (1 skipped: exchange_calendars)`, 068's `342/343` is 342 passed, 1 skipped (logs/audit/2026-11-17-068.md), and 073's is `414/415`. 065's `49/49` was a single test file with no skip.
   - Root cause: `<total>` is not defined in i2-builder.md L25 or in LOG_FORMAT (`tests \d+/\d+\b.*`). I2 types both numbers from pytest's summary by hand, which is the RI-006 shape (a hand-made count in a log line) that the regex cannot catch.
   - The line stays as it is: logs are never edited (item 045). The correct value is `tests 411/412`. Proposed as P2 (BUG).

## Proposed follow-up items (for the orchestrator to open; IDs from `check_pipeline.py --next-id`)
- **P1 (BUG): the drift test misses Bash granted to a no-shell agent in YAML flow-list form.**
  - Evidence: probe x4 above (`tools: [Read, Write, Glob, Grep, WebSearch, WebFetch, Bash]` on r1 → 7 passed). Found in this audit of 072, tests/test_agent_tools.py `_field`/`agent_tools`.
  - Root cause: `_field` splits on commas and keeps any token. An unrecognised token (`Bash]`, `"Bash"`) silently counts as "not Bash".
  - Guardrail:
    - Parse the flow form: strip `[`/`]` and surrounding quotes.
    - Make every entry match `^[A-Za-z]+(\(.*\))?$`, otherwise error `"unparsed tools: entry <x> (item 072 follow-up)"`, never ignored.
    - Add fixture cases g (flow list with Bash → Bash present), h (flow list without Bash → absent) and i (an unparsable entry → error).
